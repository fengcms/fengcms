# 留言提交与后台回复一致性审阅报告

日期：2026-10-28。代码基线：`29b055c`，开始时工作区干净。

**本轮确认 6 项问题：P1 一项、P2 五项。** 应优先处理未审核留言直接公开，以及普通回复表单因空字段保存失败。另有旧回复覆盖、删除与保存交错误报成功、批量删除不可恢复重试、提交结果不确定时重复创建，以及确认框出现在请求完成之后的问题。

本轮只交付报告与文档索引，不修改程序、配置、正式测试源码或原站点模板。既有 **617 项主回归通过**，但没有覆盖下述失败场景；这不改变此前 SC、CM、MS、RA、DB、TC 专项的既有关闭结论。

## 范围与证据条件

审阅前台 `messageController`、`messageModel`、`message.html`、`message_add.html`，后台留言控制器、模型、列表与回复模板，以及验证码、会话、分页、数据库执行和 Validform 回调链路。

独立 HTTP 探针使用带 `f_dev_meta` 标记的随机隔离数据库、两个独立管理员会话、匿名访客会话、六个 PHP CLI Server 工作子进程和完整站点副本。副本的 **326 个 PHP 文件**与仓库逐文件 SHA-256 一致。验证码由真实图片接口生成；探针仅读取自己创建的测试会话中的验证码进行提交，没有把猜中验证码视为攻击能力。

旧表单覆盖与批量失败分别在 **InnoDB、MyISAM** 留言表重放。删除与保存交错另用 InnoDB 行锁确定执行顺序。浏览器使用本轮临时后台账号，覆盖真实后台 iframe 回复失败，并查看匿名留言列表；没有在浏览器完成前台验证码提交。

## LM01 未审核留言直接进入匿名列表

位置：[前台列表模板第 27 行](../template/message.html#L27)、[前台模型第 4 行](../app/model/messageModel.php#L4)、[分页查询第 398 行](../system/core/page.php#L398)。

链路为：访客 POST `/?controller=message&operate=save` → 服务端固定写入 `status=0` → `messageController::index` 渲染模板 → 模板直接调用 `sqlpage("message","2")`，没有状态条件 → COUNT 和列表 SELECT 都覆盖未处理记录。模型的 `page()` 虽然使用 `status=1`，这条实际展示链路没有调用它。

**重放：**使用真实 CSRF 与验证码提交唯一标题，同时伪造 `status=1`、`reply=forged`。服务端正确忽略伪造字段，数据库实际仍为 `status=0`、`reply=NULL`；随后全新匿名会话 GET 留言列表，HTTP 200 正文包含该唯一标题。浏览器也显示了隔离库中状态为 0 的未回复夹具。

**影响与修复要求：**当前待处理/已回复状态没有成为公开展示边界。应先明确回复与发布的业务关系；按当前模型的 `status=1` 规则统一公开查询、总数和分页条件，避免只在循环里隐藏条目。若产品确实要求留言提交即公开，也应明确修改状态契约，而不能保留相互矛盾的两套查询规则。

**验收：**未处理、已发布、撤回三种状态逐一检查匿名正文、总数及各分页；混合状态数据中，隐藏记录不能占用公开分页名额。需要先修复 LM04，才能经现有保存入口可靠提交 `status=0`；本轮不声称该入口已经支持正常撤回。

## LM02 旧回复覆盖与并发删除误报成功

位置：[后台回复保存第 66 行](../admin/app/model/messageModel.php#L66)、[存在检查与 UPDATE 第 72 行](../admin/app/model/messageModel.php#L72)、[回复表单](../admin/template/message/reply.html#L51)。

两份真实回复页没有携带服务器版本。InnoDB、MyISAM 下分别让两个独立会话读取同一条记录，A 保存 `FIRST_APPROVED` 成功，再由 B 的旧表单保存 `SECOND_OLD_FORM`，两次响应均为 `status=y`，数据库最终只剩 B 的回复。这里使用能够通过现有校验的请求，旧表单问题不依赖 LM04 的空字段错误。

另在 InnoDB 中：测试连接锁定一条已存在记录 → B 提交回复，已通过普通存在检查，UPDATE 进入等待 → 持锁连接删除记录并提交 → B 更新影响 0 行，却因 `update(...)>=0` 返回 `status=y`。实际记录已经不存在，且没有新建回来。探针核对了等待中的真实 UPDATE，而非只依赖固定延时。

**修复要求：**在服务端为编辑基线提供版本并原子核对，旧版本返回明确冲突并保留输入；让存在性、版本和更新结果具有一致语义。不能简单把 `>=0` 改成 `>0`，否则原本合法的同值保存会被误报失败。删除后到达的旧保存应明确报告不存在或冲突。

**验收：**双会话旧表单、同时提交、同值重试、删除后保存及 UPDATE 等待期间删除；核对响应与最终行状态。两种引擎都应验证，不能只依赖 InnoDB 事务解决存量 MyISAM 的覆盖问题。

## LM03 批量删除部分完成且原请求重试停滞

位置：[后台批量删除第 50 行](../admin/app/model/messageModel.php#L50)、[删除调用](../admin/app/model/messageModel.php#L42)。

在两种引擎下分别准备 A/B/C，按顺序提交真实批量删除请求。在隔离表上仅为 B 注入 BEFORE DELETE 故障：请求返回 HTTP 500；A 已消失，B/C 仍存在。移除故障后，以相同 ID 列表和 CSRF 重试，接口返回 `status=n`；因为 A 的删除影响 0 行，循环立即返回，B/C 仍未处理。

**影响：**统一失败响应掩盖了已完成的不可恢复删除；原请求不能自行继续。InnoDB 在当前逐语句自动提交实现下同样部分完成，不能把本轮结果仅归因于 MyISAM。

**修复要求：**明确批量的整体或逐项语义，反馈已删除、已不存在、失败和未处理项；让原请求能安全重试，避免在已经完成的前项停止。可复用既有内容管理的批量预算和结果协议，但需独立覆盖留言调用链；MyISAM 不得宣称可用普通事务回滚所有已删记录。还应设整个批次的等待预算，不能只有每条数据库语句的超时。

**验收：**首、中、尾项失败，已不存在 ID、同次列表重试、混合状态及锁等待。确认没有未说明的部分删除，并验证页面能够处理明细而非一律提示整批成功或失败。本轮实际重放的是 SQL 故障与缺失前项，没有重放 500 条累计锁等待超时。

## LM04 正常回复因空字段失败且文本被破坏

位置：[后台控制器保存入口](../admin/app/controller/messageController.php#L68)、[旧过滤函数第 190 行](../system/common/filter.php#L190)、[过滤数组第 248 行](../system/common/filter.php#L248)、[模型类型校验](../admin/app/model/messageModel.php#L70)、[回复页回调](../admin/template/message/reply.html#L23)。

控制器先对整份 POST 调用 `lib_replace_end_tag_array`。其中 `lib_replace_end_tag` 对 `empty($str)` 返回布尔值 `false`，所以合法空字符串及 `'0'` 在模型校验前已变成错误类型；普通文本同时被 HTML 编码、删除斜线和替换标点。

**重放结果：**

- 真实回复表单回填标题、正文及空的昵称/QQ/电话/邮箱，填写非空回复并提交，返回 HTTP 400“留言内容不正确。”，数据库回复未保存。浏览器在真实后台 iframe 重放同样失败，并跳到结果页，输入不再保留。
- 单独提交 `status=0` 或清空 `reply` 也为 400。这不是模型允许状态值 0 就代表整个 HTTP 链路能接受 0。
- 提交普通回复 `https://example.test/a/b`，接口成功，但实际存储为 `https&#58;example&#46;testab`。模板默认转义后也不能把已经删除的路径恢复成原 URL。

**修复要求：**先按字段验证原始类型、长度和业务语义，保留合法的空值及零值；普通留言和回复按文本存储，在展示处继续默认转义，不能靠删除 `/` 或预先 HTML 编码来保证安全。返回字段错误时保留编辑内容。检查现存实体数据兼容，但不要对历史数据无条件批量反转义，避免二次解释或改变用户原文。

**验收：**可选字段全空、数字零、清空回复、中文、换行、URL、引号、尖括号及实体文本的保存/回填往返；覆盖实际 iframe 的失败输入保留。上述修复不得移除 CSRF、角色权限和默认模板转义。

## LM05 结果不确定后重试产生重复留言

位置：[前台插入与验证码消费](../app/model/messageModel.php#L19)、[提交表单](../template/message_add.html#L64)。

**重放：**第一次真实请求已经成功入库，探针主动丢弃其成功响应，模拟客户端无法判断保存结果；以原 CSRF、验证码和相同内容重试，返回 `status=c`。用户按提示刷新验证码后再次提交相同内容，又返回成功，得到不同 ID，数据库中存在两条相同留言。本轮是丢弃实际响应的等效结果不确定样本，没有宣称在网关层真实断线。

同会话并发双击是另一种结果：两次请求因会话锁与验证码消费，分别返回 `y/c`，数据库只有一条。本轮没有把正常双击描述为直接产生两条，也不主张按正文全局去重，因为用户可能有意发布内容相同的新留言。

**修复要求：**以服务器签发、绑定当前表单和会话的提交标识识别同次操作，在有限时间内能够恢复已经确认的结果。插入前的真实 SQL 失败仍须允许重试，首次请求仍须验证验证码和 CSRF；已保存结果的恢复不能退化为绕过验证码的新建入口。可参照资源上传的结果不确定处理，但不要把 CSRF token 当作每次创建的唯一标识。

**验收：**正常并发双击、插入前失败、保存后丢响应、原表单带新验证码重试，以及新开表单有意发布相同内容。核对同次操作只创建一次，独立操作仍可正常创建。

## LM06 确认框出现在请求完成后

位置：[提交回调第 21 行](../template/message_add.html#L21)、[按钮调用第 39 行](../template/message_add.html#L39)、[Validform 的响应处理](../js/validform/validform.js#L8)。

按钮直接调用 `data.ajaxPost()`，而 `confirm("您确定要提交留言吗？")` 位于 Validform 的 `callback` 内。所用库从 AJAX 成功或错误处理器调用该回调，因此这不是发请求前的确认。

本轮 Node 探针执行了模板中的实际内联脚本，捕获它注册的回调；按库的成功响应语义调用后，记录顺序为“成功结果到达 → 弹提交确认”。让确认返回 `false`，只会停留在表单，不能撤销已经完成的操作。另核对了绑定库的真实响应处理代码。该检查是回调级验证，不冒称已在浏览器填写验证码、提交并取消确认的完整重放。

**修复要求：**把确认放在 `beforeSubmit` 或调用提交之前；结果回调仅处理真实结果。取消时不得发出保存请求，失败时保留输入，网络错误与验证码错误应显示对应提示。LM01 修复后成功提示也应与“待审核”契约相符。

**验收：**取消确认时网络面板无保存 POST、数据库不变；确认提交仅发送一次；分别覆盖成功、验证码失败、字段失败和响应不确定。最终用真实浏览器补齐完整交互验证。

## 已验证的正确行为和资源边界

- 前台不能通过提交字段指定发布状态、回复或创建时间；成功验证码在一次留言提交后消费。同会话并发两次保存只新增一条。
- 对本轮唯一标题注入插入前 SQL 错误，实际请求为受控 500；移除故障后原验证码可重试，最终仅有一条。字段长度校验失败后修正输入也可重用验证码。
- 旧标签页使用旧验证码会同时清除会话中更新的验证码，随后新标签页也验证失败。当前是会话共享、失败即失效的策略；记录为多标签页体验限制，未另计一项漏洞。验证失败限流的既有回归通过，本轮没有重新做大规模对抗或吞吐测试。
- 隔离库增加 400 条各 5000 字节的待处理正文：深页请求被限制到有效页，前台每页不超过 2 条；后台待处理第一页约 116 KB，单次读取约 7.47 ms。前台深页约 85.15 ms。这些是单次诊断观测，不是容量上限或性能承诺。
- 待处理统计的 EXPLAIN 为 `type=ALL`、无可用索引，本轮估算扫描 411 行。可根据实际规模评估状态索引和列表字段裁剪，但本轮没有证明性能故障，不另编号。
- 超过 500 个批量 ID 的请求在写入前返回 400，数据库数量不变。批量参数校验有效，不能替代 LM03 的执行阶段恢复设计。
