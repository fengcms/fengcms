# 数据库备份与恢复一致性修复

依据[数据库备份与恢复审阅](DATABASE_BACKUP_RECOVERY_REVIEW_2026-10-28.md)，按 DB02 → DB01 → DB03 → DB04 处理。保留预览、一次性确认、受限 SQL 解析、导入前自动备份和整体表交换；不改变前台模板语法或备份格式。

## 规划与实现

1. **DB02：恢复停写边界。**同一数据库使用 8 个 MySQL 命名锁槽位。普通 CMS 写入取得一个槽位；备份与恢复按固定顺序取得全部槽位，等待已进入的写入完成后才预检和自动备份。入口包括后台及公开 POST、模型结构锁、内容与栏目锁、独立上传接口和公开页面的浏览计数。导入入口先取得全部槽位，再执行原有导入锁；写入超时明确失败，不会在自动备份之后报告成功并被交换覆盖。独立自定义代码或外部 SQL 必须参加同一协议，或在恢复时由站长另行停写。
2. **DB01：备份结构快照。**在协调锁外仍可能发生站长直接执行的 DDL。备份设置数据库锁等待上限，在取得所有表及视图的读锁后重新检查对象、DDL 和列；导出结束、解锁之前再次复核。结构变化则清理临时文件并拒绝发布，避免旧建表语句与新行列混用。
3. **DB03：中断恢复记录。**导入在创建任何暂存表之前，将随机操作 ID、数据库、阶段及每个正式/暂存/旧表的精确映射写入私有目录。交换前记为 `pre_swap`，交换并核对后记为 `committed`。连接中断时保留记录；后续备份与导入预览拒绝继续。后台「导入备份」提供 POST/CSRF 保护的恢复按钮。恢复用新连接核对每张表的存在状态：交换前清理明确登记的暂存表，交换已发生但尚未提交时原子回退，已提交时只清理剩余旧表。状态不完整即停止，绝不按名称前缀盲删。恢复后需重新预览备份。
4. **DB04：锁等待预算。**备份连接超时 5 秒，数据库会话 `lock_wait_timeout=5`；写入屏障、连接、结构检查、读锁、导出均计入总计 120 秒的应用期限。数据库锁持续被占用时失败、释放文件与数据库锁，且不发布备份。

恢复记录在私有备份目录，权限为 `0600`，无需数据库迁移。部署前仍须保存数据库、上传资源、运行配置及对应源码的配套快照；后台 SQL 备份只覆盖数据库。

## 验证

- `./bin/dev check`：PHP 语法通过。
- `./bin/dev test`：主 HTTP/数据库回归 598 项通过，独立导入与 MyISAM 结构回归通过。新增隔离回归验证 MyISAM/InnoDB 结构竞态、新增表与视图、自动备份后的写入屏障、连接被终止后的精确恢复和原备份重试，以及持续锁阻塞后再次备份。
- 真实后台 iframe：开发库一次性账号进入「系统 → 数据库管理 → 导入备份」；使用仅引用开发标记表的临时恢复记录验证提示、恢复按钮、成功跳转及表单重新出现。临时账号与恢复记录已精确清理并核对为零。

仍待独立演练：外部 SQL 写入者未参加停写协议、交换后进程强杀及旧表删除途中磁盘或连接故障、磁盘耗尽、MariaDB 专项并发和线上虚拟主机的实际权限与请求时限。遇到恢复记录的对象状态不完整时，程序会拒绝自动处理，需先在站点副本核对。
