# TC06 模板内容刷新关闭复审

日期：2026-10-28。代码基线：`dc92fa2`；修复实现：`a737c54`。开始时工作区干净。对照[原失败报告](TEMPLATE_CACHE_TC04_CLOSURE_2026-10-28.md)及[开发方修复说明](TEMPLATE_CACHE_TC06_REMEDIATION_2026-10-28.md)。

**结论：TC06 可以关闭。** 绑定源码分别配合绑定缓存、原生缓存卷时，正常后台保存后的首个和后续请求均能显示新内容，不再因源码时间戳落后而持续复用旧正文，无需人工清缓存。原生卷的快速保存样本中还自然出现了 3 次源码时间戳落后的情况，均刷新成功。

本轮只新增报告与索引，不修改程序、配置、正式测试源码或原站点模板；测试夹具仅写入隔离副本。未部署、重启原服务或推送。

## 实现核对

| 核对点 | 证据与判定 |

## 原失败场景重放

使用带 `f_dev_meta` 标记的随机隔离库、真实后台认证及 CSRF、未修改 PHP 源码的完整站点副本和六个 PHP CLI Server 工作子进程。源码始终绑定挂载；编译缓存分别使用副本绑定目录和两个本轮新建的 Docker 原生卷。运行配置与锁位于临时容器私有目录。副本的 **325 个 PHP 文件**与仓库逐文件 SHA-256 相同。

确定性样本先正常保存并渲染 A，然后只把本轮旧编译文件的时间设到未来，再通过真实后台保存 B。保存后、第一次读取前，核对源码确实早于旧缓存且旧缓存内容未变。该手段用于稳定制造原报告的时间顺序，没有修改保存实现，也没有通过清缓存帮助样本通过。

| 场景 | 绑定缓存 | 原生缓存卷 |
| --- | --- | --- |
| 正常保存后源码落后旧缓存约 1 秒 | 首个请求及等待 1 秒后的请求均为完整 200、正文精确等于 B。 | 同左；实际时间为源码 `1793164680`、旧缓存 `1793164681`。 |
| 正常保存后源码落后旧缓存约 120 秒 | 两次请求均显示 B；编译头摘要与保存字节相符，旧 A 不再出现在产物。 | 同左；实际时间为源码 `1793164681`、旧缓存 `1793164801`。 |
| 源码与缓存时间相等，内容变化 | 自动刷新为 B。 | 自动刷新为 B。 |
| 父模板不变，子模板正常保存且时间落后 | 父模板两次 include 均显示新子模板，父产物内容未变。 | 同左。 |
| 刷新后源码不变 | 再次读取不更换编译 inode 或 mtime。 | 同左。 |
| 80 次正常快速保存与立即读取 | **80/80** 正文精确匹配新内容；自然落后次数 0。 | **80/80** 精确匹配；其中 **3 次自然落后**也立即刷新。 |

两种存储各有 **14 项独立断言通过**。快速保存样本不修改时间戳，也不调用清理接口；自然落后次数仅描述本轮实测，不作为发生概率估计。其他确定性样本明确使用了人工时间差，不与自然样本混淆。所有通过均核对实际 HTTP 状态和正文，并检查源码/产物关系，未将“保存成功”单独视为刷新成功。

## 开销与验证边界

内容校验现在每次读取模板源码并计算摘要，开销随源码字节数和本次渲染涉及的模板数量增长；发生重新编译时，升级锁后还会复查。源码未变不重复写产物，同一请求重复 include 会复用持有结果。本轮没有进行吞吐量或大型模板基准测试，不宣称性能没有变化。该实现足以解决本次跨文件系统时间戳导致的正确性问题。

独立 HTTP 验证使用 CLI Server；主回归经过本地 Nginx/PHP-FPM。生产 OPcache 配置、网络文件系统、多节点锁和更高负载仍需按部署环境验证。本轮未做浏览器 UI 操作，也未重新认证全部并发故障组合。
