## 隔离重放与证据范围

使用随机命名、带 `f_dev_meta` 标记的隔离库，由仓库初始化与迁移函数建立完整 CMS、临时超级管理员及草稿。分别将 `f_article` 内容表设为 InnoDB、MyISAM，其余表保留初始化结构。增加 70 张空夹具表后，共 93 张正式表，仍处于 100 表导入上限内，用于增加交换后核对阶段的观察窗口，不作为容量测量。

HTTP 用例经过实际登录、会话、CSRF、编辑签名、预览 nonce 与确认。通过导入服务已有回调在真实自动备份后暂停调度，再使用正常 HTTP 请求排队。随后放行导入，在整体交换后的 `SELECT * FROM f_view_field LIMIT 0` 核对期间，对精确记录的隔离导入连接执行 `KILL CONNECTION`。

两种引擎均在第一次调度尝试中捕获该窗口：正式内容已由导入前 C 变为历史备份 A，持久阶段仍为 `pre_swap`，93 张旧表完整存在。没有手工交换表来替代中断，没有修改业务实现或伪造查询返回值。

## 双引擎结果

以下各项在 InnoDB、MyISAM 内容表下分别完成：

| 场景 | 实测结果 |
| --- | --- |
| 已进入等待的编辑请求 | 确认请求在数据库槽位上排队；连接中断、屏障释放后返回 **409**，提示“导入尚待恢复”，正式内容保持 A。说明检查发生在取得槽位以后，没有仅凭进入请求时的旧状态放行。 |
| 中断后重新打开编辑页并提交 D | 编辑页可读取、取得新签名；提交返回 **409**，正式表仍为 A，没有保存成功确认。 |
| 待恢复期间新增字段 | 返回 **409**，没有对应物理列。 |
| 待恢复期间上传合法 PNG | 实际 multipart 返回 **409**；按独立内容哈希核对无最终文件，按请求键核对无上传状态行。 |
| 新会话重新登录 | 登录成功，受保护的数据库恢复页返回 **200**，恢复入口仍可访问。 |
| 正常显式恢复 | POST `recoverimport` 返回 **303**，正式内容回到 C，待恢复记录及登记的旧表/暂存表均清除。 |
| 无关但名称相似的表 | 在隔离库创建未登记的 `cmsimp_*` 夹具，恢复后该表及标记行仍存在；随后只清理本轮夹具。 |
| 恢复后正常编辑 E | 重新读取编辑页后保存，返回 **200、`status=y`**，数据库确认为 E。 |
| 原备份重试 | 实际 HTTP 重新预览、确认，返回 **303**，内容恢复为 A，无待恢复记录。 |

原先“中断后确认 D，再由恢复删除 D”的路径已不再成立。

## 已有冲突数据与旧记录保护

为验证旧版本可能已经确认过的修改，在上述真实中断留下的隔离状态中，仅用 SQL 修改本轮草稿标题为 D，模拟绕过新屏障的既有写入；这不代表当前 HTTP 保存仍会接受 D。

两种引擎下执行实际恢复接口均返回 **500**，提示“正式数据已变化或缺少核对记录，停止自动回退”。数据库仍为 D，对应旧表仍为 C，持久恢复记录字节未变。程序没有交换或删除这些数据。

另外，仅从本轮隔离恢复记录中移除一项指纹，模拟交换后的旧版记录。恢复同样返回 **500** 并拒绝自动回退，正式表、旧表和待恢复状态均保留。

为了继续检查无冲突分支，测试显式撤销了自己注入的标题修改，并还原本轮记录文件，然后才执行成功的恢复。程序未自动合并或丢弃冲突；真实站点出现此提示时，仍应按[操作说明](DATABASE_IMPORT.md)先保全，在独立副本比较并人工决定。
