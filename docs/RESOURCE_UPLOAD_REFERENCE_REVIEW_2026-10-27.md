日期：2026-10-27。代码基线：`95d8224`，开始时工作区干净。

**结论：确认 RA01、RA02 两项 P2 问题，以及 RA03 一项 P3 恢复与存储效率问题。** 优先修复多图确认保存时的静默引用丢失，并补齐图片上传的实际可解码校验；响应丢失后的重试还需明确同次操作的幂等契约。静态列表分页、现有资源上限和本轮测试的上传错误状态释放均符合预期。

本轮只新增报告和索引，不修改程序、模板、配置或正式测试源码，不执行生产操作或推送。P2 表示影响正常内容保存或上传可用性的一致性问题，P3 表示恢复体验及资源效率改进，不使用安全漏洞 CVSS 评级。此前内容写入、模型结构等专项的关闭结论不变。

## 范围与方法

覆盖 `admin/api/upload.php`、`files.php`、`thumbnail.php`，以及 `editor.js`、`resource-picker.js` 和图片、多图、附件字段的保存回显链路。验收参照[资源选择器记录](RESOURCE_PICKER_UI_PLAN.md)与[编辑器迁移记录](EDITOR_MIGRATION.md)。

专项在独立开发标记数据库中创建临时超级管理员、模型、自定义字段和两条草稿，通过真实 HTTP、CSRF、内容创建键及编辑签名调用当前代码。隔离 HTTP 服务使用 PHP 8.4、多进程及 `www-data` 用户；上传实际写入容器上传卷，文件均有独立标记或逐个 URL 清单。浏览器使用真实后台 iframe，未替换业务方法或注入选择器状态。

中断场景分别为“只发送部分 multipart 后断开”和“完整发送后不读取响应即关闭连接”。后者模拟客户端不知道服务器是否完成的结果不确定状态，不声称完成了真实移动网络弱网测试。上传适配器的异常分支另用实际脚本和模拟 XHR 检查，与真实 HTTP 结果分开记录。

## RA01 上传成功不代表图片可解码

**位置与数据流：**`$_FILES['imgFile']` → [MIME 和头信息检查](../admin/api/upload.php#L45) → [随机命名并移动文件](../admin/api/upload.php#L59) → 返回 URL → 图片字段或富文本正文 → 内容保存。上传接口使用 `getimagesize()`，实际解码只发生在后续的[缩略图接口](../admin/api/thumbnail.php#L12)。

**独立复现：**构造带合法 PNG 签名、IHDR、文本标记和结束块，但没有可解码像素数据的测试文件。`finfo` 返回 `image/png`，`getimagesize()` 返回尺寸，而实际 GD 解码返回失败。按正常 multipart 上传，得到 HTTP 200、`error=0` 和资源 URL；用该 URL 请求缩略图，返回 HTTP 400。

通过正常内容接口将该 URL 同时写入自定义图片字段和正文 `<img>`，保存返回成功；数据库和编辑页均保留了引用。因此问题不止于资源库出现一个占位图，而是新上传的不可用资源已经作为成功结果进入内容。

**影响：**损坏图片可被误认为上传完成并继续保存，最终显示失败。现有缩略图占位处理能容忍损坏或历史资源，本轮不把这个降级机制认定为缺陷；需要补齐的是上传成功前的可用性检查。

**修复要求：**保留大小、扩展名、MIME 和像素上限，在受资源限制的实际解码校验通过后再发布图片 URL。失败应返回明确提示且不留下最终资源。不得改成扫描二进制中的 PHP 字符串，也不能为校验而无条件重编码所有文件、破坏正常 GIF 等文件的原始内容。解码本身的时间与内存开销需要纳入边界。

**验收：**本轮无像素数据的 PNG 在上传阶段被拒绝，无最终文件；补充其他损坏和截断图片样本。合法图片仍能上传、取缩略图并保存引用，保留既有字节完整性、合法二进制内容和资源上限回归。

## RA02 多图恢复丢失已有引用

**位置与数据流：**数据库 `gallery` → [多图编辑字段](../admin/template/system/form/batchpic.html#L5) → `field.value` → [截取前 60 项并过滤 URL](../admin/js/resource-picker.js#L77) → [确认回填](../admin/js/resource-picker.js#L80) → [完整覆盖字段值](../admin/js/editor.js#L118) → 正常内容保存。

选择器初始化时只把 `initial.slice(0,60).filter(validURL)` 放入 Map。`validURL()` 又只接受特定上传目录下的站内相对地址；不被选择器接纳的原值没有单独保留，确认时只回填 Map 中剩余的项目。

### 超出选择上限的已有值

通过正常字段和内容接口保存 61 个实际存在的站内图片 URL，服务器完整接受。编辑页输入框仍包含全部 61 项，最后一项为 `g061.png`。

在实际 iframe 打开多图选择器，它显示“已选择 60 张图片”，没有说明丢弃了第 61 项。直接取消，原字段仍保留 61 项；重新打开，不作改选，点击“使用所选图片”并保存，数据库只剩 60 项，`g061.png` 的引用消失。原图片文件仍存在，丢失的是内容引用。

### 未超上限的绝对地址

另通过正常接口保存两项：一个站内相对地址和一个指向测试图片的同源 HTTP 绝对地址。编辑页回显两项，但选择器只显示“已选择 1 张图片”；直接确认并保存后，数据库只剩相对地址项。该场景与 60 项上限无关。

以上是实际保存及浏览器回填结果，不是仅根据源码推测。测试代表接口当前允许保存的内容，不声称已经在某个客户站点发现同样的存量数据。

**影响：**用户只查看选择器再确认，就可能在无提示情况下改变原内容；正常保存会将丢失结果持久化。“一次最多选择 60 项”不能自动视为可以截断已存字段的授权。

**修复要求：**区分选择器本次可管理的项目与原有完整字段值。对超限或当前资源库不支持的已有 URL，保留原值或明确阻止有损确认，并提供清楚的兼容处理；不能无提示过滤后覆盖。若决定限制新写入数量，应在服务端形成一致契约，同时保护已经存在的内容。URL 规范化、顺序及回填应保持可往返。

**验收：**分别重放 61 项和两项混合地址场景。打开、取消、无改选确认与保存后，原引用不得静默消失；若需要迁移或删减，界面必须明确指出具体受影响项。继续覆盖正常单图、多图、附件、清空选择及失败后保留输入。

## RA03 结果不确定时重试产生重复资源

**位置与数据流：**[上传请求](../admin/js/editor.js#L24)只提交文件与 CSRF → 服务端每次[生成新随机名](../admin/api/upload.php#L59)并移动文件 → 客户端超时或网络错误 → [队列重试](../admin/js/resource-picker.js#L172)再次上传同一 File。没有标识同次上传操作的请求键或可恢复结果记录。

**独立复现：**完整发送一张带独立内容标记的合法图片，不读响应即关闭连接。通过字节哈希确认服务器已生成一个最终资源。随后用相同文件名和相同字节重试，上传成功并生成另一随机 URL；最终存在两个不同路径，内容一致。

**影响与级别：**结果不确定时，“重试”可能重复占用存储，客户端也没有取回首次结果的能力。本轮没有观察到文件覆盖或内容丢失，因此列为 P3 恢复与效率改进，不把它等同于前两项的数据或可用性问题。

该现象与文档已经明确的“取消弹窗后保留成功上传的文件”不同。取消保留策略可以成立；这里是同一失败项的重试无法区分首次请求是否已经完成。

**修复建议：**为同一队列上传操作生成稳定请求标识，重试复用，服务端绑定账号、目录和载荷并记录完成结果；返回既有结果前核对对应文件仍存在。不要用全局文件哈希去重替代操作身份，避免改变用户主动重复上传的语义。若暂缓实现，至少明确告知不确定结果及查找已上传资源的方式，并保留本项状态。

**验收：**首次已落盘、响应未被客户端取得时，同次重试可返回原资源结果或有明确的恢复提示；不能悄悄持续生成副本。另覆盖上传只完成一半、首次未落盘、键与载荷不符以及用户主动重新上传同一文件等情况。

## 修复顺序与交付要求

建议按 **RA02 → RA01 → RA03** 推进。先防止正常确认操作静默丢失引用，再确保新上传图片实际可用，最后明确不确定结果的重试契约。每项提交保留认证、POST/CSRF、会话保护、参数与路径验证、像素及大小上限、随机命名和上传目录脚本禁执行规则。

补充能够捕获上述原反例的正式回归，并在真实 iframe 核对选择、取消、重试和保存。不要通过自动删除未引用文件来代替重试设计，或把取消弹窗扩展为会删除既有资源的动作。真实弱网、所有移动浏览器、磁盘耗尽和进程强杀恢复未在本轮覆盖，应独立验证。
