# 性能优化复审闭环与下一步计划

日期：2026-10-27。依据：[性能优化复审回复报告](PERFORMANCE_OPTIMIZATION_REVIEW_2026-10-27.md)。本轮处理 R1–R4；没有修改 `template/`、`admin/template/` 或原有模板语法，也没有部署生产站点。

## 复审问题处理结果

| 项目 | 修正与针对性证据 | 提交 |
| --- | --- | --- |
| R1：带注释的事务污染共享连接 | 模型 `query()` 的原生 SQL 始终使用该模型的独立连接；`excsql()` 仅对明确的普通读取复用连接，带 SQL 注释、用户变量、连接锁等语句独立执行。开发库 InnoDB 测试分别使用块注释、行注释、MySQL 可执行注释、普通 `BEGIN` 和 `START TRANSACTION`：事务内写入被回滚，另一模型的普通写入保留，连接 ID 不同。临时表、用户变量和连接级锁也有归属测试。 | `fcff584` |
| R2：事务提交后缓存旧值 | 请求内修订号在独立事务 `COMMIT`、`ROLLBACK` 及原生 SQL 执行后保守更新。使用独立随机前缀的 InnoDB 栏目和字段表，验证未提交时普通读取仍见旧值、提交后见新值；覆盖 `affairs()`、原生 `query()`、`excsql()`、回滚和普通更新。 | `54a75c3` |
| R3：Fatal 日志漏报 | 诊断汇总识别 PHP 未捕获异常的 `文件:行号` 首行与后续 `thrown in ... on line ...`，同一错误计一次；Parse error 也纳入失败门槛。测试覆盖 Warning、Deprecated、Notice、Parse、多行 Fatal，以及容器内真实触发的 Fatal；汇总不输出异常消息。 | `86181b1` |
| R4：模型包导入持有 Session 锁 | 模型导入在认证、CSRF、nonce 验证并消费预览状态后释放锁。HTTP 回归用独立连接暂时锁住模型表，使真实导入停在数据库等待阶段；同会话资源请求仍返回，第二次确认立即拒绝。另验证失败导入后 nonce 不可重用、会话仍有效。 | `13bd307` |

R2 的修订号采用保守失效：某些不确定语义的原生 SQL 即使只是读取，也可能使请求内快照重建。这保证提交后的可见性，后续需用代表性数据测量额外查询成本，再决定是否增加经过审计的专用读取入口。

- `./bin/dev test`：478 项 HTTP/数据库回归通过；独立的原生 SQL、事务缓存、栏目和驱动回归通过；隔离数据库导入演练通过。

- `python3 tests/php-diagnostics-regression.py --live-php`：标准诊断格式和实际 PHP Fatal 均正确触发失败门槛，输出无异常消息。

以上是本地开发环境和隔离测试的结论，不等于已测量真实站点吞吐量。数据库锁控制的并发用例验证了模型导入的会话行为；它不代表所有导入包大小、数据库引擎或共享主机配置。

## 下一步优化顺序

1. **建立代表性性能基线。** 在维护者控制的隔离数据库副本中，固定 PHP/MySQL 配置、数据规模和缓存状态，测首页、深层栏目、内容页、站点地图、资源列表及搜索的 SQL/连接数、内存、中位数和 P95。先检查本轮保守缓存失效是否增加重复查询；不把小型开发库的耗时外推到线上。
2. **决定搜索优化。** 对全站与指定模型搜索分别测空结果和高命中，保存 `EXPLAIN` 与结果集对照；再评估字段能力批量读取、字段裁剪、去重、索引或独立搜索方案。任何 `UNION`、排序、分页或发布状态变化都必须通过结果一致性测试。没有可复现收益则保持当前 SQL。
3. **逐模块收敛代码契约。** 继续把经过验证的请求参数显式传入业务方法，保留旧模板与 PHP 调用入口；按模块增加静态检查和格式规则，逐步拆分大型综合回归。不要将全仓格式化与业务性能修改放进同一提交。

每个实施节点独立验证、按 `type(scope): 中文描述` 提交。模板文件和调用语法保持不变；涉及索引或结构变更时先在隔离副本演练并准备回退快照。
