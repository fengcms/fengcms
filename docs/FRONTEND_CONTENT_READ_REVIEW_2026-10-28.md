## FR01：停用模型仍可通过栏目页读取已发布内容

内容详情控制器会查询 `f_module` 并要求 `type=1 AND status=1`，不满足时返回 404（`app/controller/contentController.php:24-29`）。栏目控制器只根据栏目 ID、英文名和 project 取栏目记录，没有核对对应模型是否启用；随后将 module 类型栏目交给栏目模板（`app/controller/classifyController.php:49-75`）。模板调用的 `moduleModel::page()` 只过滤内容行的 `status=1`，没有检查模型状态（`app/model/moduleModel.php:277-280`）。

因此，当自定义模型被后台停用但栏目和已发布内容仍保留时，访客可通过现存栏目 URL 读取该模型的标题、列表项及模板选出的内容字段；点击详情链接则会被详情控制器拒绝。导航树查询只按 `classify.nav=1` 过滤，没有关联或筛除停用模型，已停用模型的栏目仍可能出现在站点导航中。

这与既有内容请求契约“停用模型的内容路由返回 404”不一致。若停用模型的定义是前台不可见，应在栏目页渲染前验证模型状态，并让导航/地图按相同规则决定是否展示该模型栏目。隔离环境 HTTP 重放未在本轮执行，实际响应与具体输出字段待验证。

## FR02：相关文章可能包含当前文章且顺序不稳定

默认文章详情模板把当前文章的 `$tags` 去除 HTML 标签后传给 `related()`（`template/article_content.html:55`）。当前文章自己的关键词也参与 `related()` 的 `tags LIKE ?` 匹配；查询没有 `id <> 当前文章 ID` 条件，也没有 `ORDER BY`，只使用 `LIMIT`（`app/model/moduleModel.php:417-424`）。

当当前文章有关键词且匹配记录数不超过默认 10 条时，当前文章自身满足查询条件，会出现在“大家都在看”列表中。匹配记录超过 10 条时，数据库没有稳定排序契约，结果可能随执行计划或数据变化而改变。

建议把当前记录 ID 显式传入查询并排除；同时定义稳定的排序方式（例如匹配相关度后再按发布时间和 ID 排序）。本轮是基于模板与查询谓词的静态确认，没有动态创建数据验证。

## FR03：相关文章查询随模型内容规模线性扫描

文章详情模板对有关键词的文章调用 `related()`。该方法为每个逗号分隔关键词追加 `(title LIKE ? OR tags LIKE ?)`，参数采用 `%关键词%`；文章表的 `title`、`tags` 没有可支持这种前导通配搜索的普通索引，安装 SQL 中仅定义主键和 `(status,id)` 索引（`install/install.sql:1-26`）。查询因此需要在已发布记录中检查标题和标签文本；关键词数越多，OR 分支越多。`tags` 字段长度上限为 255 字符，但当前查询未单独限制标签数量。

这是每次访问带关键词文章详情时发生的同步查询。大模型/高访问量下，可能形成反复的已发布记录扫描和数据库 CPU 开销。具体扫描行数、访问比例和延迟待通过隔离数据集 `EXPLAIN ANALYZE` 与基准验证；本轮没有运行数据库或压力测试。

建议先定义相关文章匹配规则及最大标签数，再根据数据规模选择可索引的标签关联表、全文索引或其他检索结构；不能仅添加普通 B-tree 索引就假设 `%词%` 查询会变快。

## FR04：默认导航每次请求全量加载栏目树

默认页头对顶级导航请求 `classid=0 AND nav=1`、最多 100 项（`template/scrap/header.html:79`）。`moduleModel::navigationRows()` 将这类请求路由到 `classifyModel::navigationRows()`；该方法先进入 `snapshot()`。`snapshot()` 执行没有 `WHERE` 和 `LIMIT` 的整表 `getall()`，读取八个字段、按 sort 排序，再在 PHP 中逐行构造 children/navigation 数组。只有树构建完成后，`navigationRows()` 才按页面请求的 100 项截取结果（`app/model/classifyModel.php:52-90`）。

请求级静态缓存只避免同一 PHP 请求内重复构造；下一个 HTTP 请求会重新读取完整栏目表。默认页头调用出现在所有使用该公共头部的页面，因此导航项的 100 条上限没有限制数据库结果读取量或 PHP 中间数组大小。栏目表较大时，这是每个前台请求的 O(栏目总数) 工作，而不是 O(实际导航项数)。

建议让普通导航查询直接在数据库按父栏目、导航状态、排序和 limit 取数；仅在确实需要完整树的地图/祖先操作中构造树，并针对大栏目表测量内存、查询行数和渲染延迟。跨请求缓存如有必要，需同时定义栏目增删改后的可靠失效方式。本轮没有运行规模测试，具体达到明显影响的栏目数待验证。

## 缓存检查与未确认项

- 在应用 PHP、控制器和模板调用点中未找到 `fcache()` 或通用 `cache()` 的页面响应缓存使用。现有 `template::tpl()` 与 `CmsTemplateCache` 管理的是编译模板缓存；此前 TC01–TC06 已审阅其刷新和并发问题。本轮没有发现新的整页缓存键串用或访客间响应复用路径。
- `moduleModel::pic()` 查询没有 `status=1` 条件（`app/model/moduleModel.php:161-164`），但仓库自带前台模板未调用该方法。若客户定制模板使用该辅助方法，草稿图片可能被列出；是否构成实际部署问题需检查其模板调用，当前标记为**待验证**，未列入已确认问题。
- 没有验证不同站点的定制模板、数据库规模、生产 Nginx/Apache 行为或客户端缓存策略。
