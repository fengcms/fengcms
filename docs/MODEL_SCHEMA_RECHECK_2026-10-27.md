## MS06 剩余问题

**优先级：P2。位置：**[取得模型锁后的身份检查](../admin/app/model/moduleModel.php#L58)，尤其第 61 至 65 行，以及其后的[物理字段读取](../admin/app/model/moduleModel.php#L75)。

取得生命周期锁后，保存方法只检查模型记录是否存在、ID 是否与等待前一致。模型删除失败时会保留同一个 ID 和 `status=-2`，因此这项检查仍通过；递归进入保存方法后也只再次检查记录存在，随后便读取物理列。

[删除流程](../system/common/model_schema.php#L145)允许“表已经 DROP，但模型行尚未清理”的可恢复状态。这一状态本身符合 MS04 的续做契约；缺口是保存入口在锁内未排除它。[ContentWrite 的状态检查](../admin/app/model/contentWrite.php#L44)发生在更后的写入路径，无法保护先执行的字段读取。

### 独立重放时序

使用两个超级管理员会话、有效编辑签名和无栏目引用的独立模型。仅在隔离库中设置两个测试条件：创建模型删除日志时暂停；删除模型配置行时抛出受控 SQL 异常。没有替换控制器或业务方法。

| 步骤 | 请求及数据库状态 |
| --- | --- |
| 1 | 会话 A 发起模型删除，已经取得生命周期锁；在写入 `model_delete` 日志前暂停，此时模型状态仍为 1，物理表存在。 |
| 2 | 会话 B 提交之前加载的内容编辑表单。它通过入口检查，读取到原模型 ID，然后等待同一个生命周期锁。通过实际 GET_LOCK 等待确认已到达此处。 |
| 3 | 解除 A 的暂停。删除流程将模型置为 -2、DROP 表、清理字段及状态；在删除模型行时触发受控异常。 |
| 4 | A 返回 409，保留原模型 ID、状态 -2 和待恢复日志，物理表已不存在，然后释放锁。 |
| 5 | B 取得锁，看到同一模型 ID，继续读取已经不存在的物理表，返回 500。私有日志记录数据库缺表异常。 |
| 6 | 移除故障，以原模型 ID 再次删除，返回 200，恢复日志清空。 |

| 元数据引擎 | 删除响应 | 排队保存响应 | 保存继续时的状态 |
| --- | --- | --- | --- |
| InnoDB | 409 | **500** | 表不存在，模型 ID 未变、状态 -2。 |
| MyISAM | 409 | **500** | 表不存在，模型 ID 未变、状态 -2。 |

这与“新请求在删除失败后才进入入口”不同：新请求可由公共路由守卫拒绝，已经通过入口并排队的请求必须在取得锁后重新验证。也不能用“模型完全删除后的旧表单返回 404”替代本场景。

**影响：**可恢复的模型删除状态仍使在途保存变为内部错误，MS06 要求的锁后生命周期校验尚未完整。该旧保存在读取结构时就失败，本轮没有观察到它额外覆盖内容或创建孤立配置；不能把此次 500 扩大解释为一次新的误删。

**修复要求：**在生命周期锁内、读取任何物理结构或执行内容 SQL 前，统一校验原模型身份、当前状态以及所需物理表是否存在，识别待删除或未发布状态并返回明确冲突。保留现有旧 ID 防复用检查，不能只在请求入口检查，也不能仅把最终数据库异常改成笼统 409。批量新增等共用生命周期的入口也应核对同类检查位置；本轮未独立重放它们在此失败状态下的全部组合。

**关闭验收：**新增能捕获上表时序的正式回归，在两种元数据引擎下证明旧保存取得锁后返回预期冲突，不读取缺失表、不产生 500、不写入新模型；原模型删除仍可按原 ID 重试完成。继续保留正常保存先完成、删除先完成、导入期间删除及同名模型重建的回归。

## 五项关闭证据与正常并发结果

### MS01 和 MS02 的字段续做

[自定义字段新增](../admin/app/model/fieldmanageModel.php#L207)先检查配置长度和保留名称，并使用绑定模型身份与载荷的恢复日志。原配置 INSERT 故障不再变成无法说明阶段的 500；保留物理列是有日志支撑的待恢复状态，解除故障后补齐配置，不重复建列。

[字段删除](../admin/app/model/fieldmanageModel.php#L294)保留字段 ID、名称和 `column_dropped` 阶段，重试时识别缺失列，完成元数据清理。本轮既核对失败响应提示，也核对了列、配置行和日志，不把 HTTP 状态单独当作一致性证据。DROP 前的字段值无法通过此续做恢复，修复采用的是完成删除的契约。

### MS03 的整批预检与逐项结果

[系统字段批量](../admin/app/model/fieldmanageModel.php#L357)展开复合字段的物理列，再预检整个选择集。为验证升级后的存量布局，本轮在隔离模型中重建了旧接口曾允许的自定义 `attrib_j` 列与配置，并保存一个旧值。提交原来的“栏目、属性”批量后返回 409，`classid` 未出现，旧值未改。

另在“属性”的配置 INSERT 处注入失败，提交“栏目、属性、日期”三个字段。首次返回：`changed=['classid']`、`failed=['attrib']`、`unprocessed=['date']`，并保留属性的恢复日志。解除故障后原样重试：`already=['classid']`、`changed=['attrib','date']`，日志清空。第三次原样提交全部进入 `already`，没有重复配置或重复列。

### MS04 的模型身份及最终日志清理

[模型删除恢复](../system/common/model_schema.php#L109)以原模型 ID 和阶段识别已经执行的 DROP，待恢复日志阻止项目代号复用。原模型行删除故障解除后，原 ID 重试完成，字段与日志均清空。

本轮还注入了最后一步日志 DELETE 失败：此时模型行已不存在，删除返回 409，模型列表的 HTTP 页面仍展示待完成项目；[控制器](../admin/app/controller/modulemanageController.php#L77)可从日志定位原模型并继续清理。完成后重建同项目代号的模型，旧 ID 请求返回 404，新模型及其表保留。

### MS05 的引用拒绝与状态清理

原“本模型父栏目 → article 子栏目”结构及两个模型的临时内容仍通过正常接口创建。删除本模型返回 409，内容表、两个栏目、跨模型内容和两类内容状态均保留，尚未创建删除日志。此处拒绝发生在 DROP 之前。

通过明确的栏目删除请求解除引用后，重试模型删除返回 200。相关回收前状态及新增幂等状态均为 0 残留，原来的缺表栏目删除错误不再出现。

### MS06 已通过的两个原并发场景

- 导入在首个字段 INSERT 处暂停时，模型保持内部状态 -2，并持有生命周期锁；另一会话删除返回 409，未 DROP。解除暂停后导入返回 303，表、已发布模型行及七条字段配置完整；随后删除成功，孤立字段为 0。
- 内容保存按原记录命名锁暂停，已进入保存流程；另一会话删除在等待期间没有完成或删表。解除记录锁后，保存返回 200 成功，删除随后返回 200，形成保存先于删除的顺序。
- 完整删除之后再提交旧内容表单，入口返回 404，没有访问缺失表的 500。

这些结果证明原先无互斥的主要路径已经修复；它们不覆盖上文的“删除中途失败而保留原 ID”状态。
