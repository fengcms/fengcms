# FengCMS v1.36 代码审阅报告

审阅日期：2026-10-26；基线：`981d5f1`（v1.36）。本报告审阅仓库当前通用代码、安装 SQL、Apache/Nginx 规则和本地回归；没有扫描客户站点、生产数据或定制代码，也没有执行生产负载测试、完整依赖漏洞扫描或第三方渗透测试。

## 总体判断

当前代码已有可运行的 PHP 8.4 开发环境，登录、路由、上传、模板和富文本的主要防护具备回归覆盖。它可以作为继续维护的基线，但**不能把“本地回归通过”解释为生产环境安全认证**。优先处理旧后台备份恢复的数据完整性、管理员可用的原始 SQL 导入，以及旧内容的输出信任边界；随后处理配置默认值、搜索扩展性和部署规则差异。

严重度按影响和触发条件评估：**P1** 为可能造成数据丢失或重大完整性问题，建议在依赖该功能或扩大部署前解决；**P2** 为需要纳入近期维护计划的安全、性能或可靠性风险。表中“确认”表示可以从当前代码直接推出，“条件风险”表示还依赖旧数据、调用方式或部署环境。没有将管理员权限内的能力描述成匿名攻击。

## 已有基础

- [登录处理](../admin/app/controller/adminController.php)使用参数化查询、失败次数限制、现代密码哈希和登录后的会话 ID 轮换；旧三重 MD5 仅用于登录迁移。[路由守卫](../system/common/security.php)限定后台方法、写操作 POST/CSRF、数字参数和模型名。
- [上传接口](../admin/api/upload.php)及部署规则限制文件类型、内容、大小和脚本执行；[富文本清洗](../system/common/richtext.php)在新内容保存时使用 HTML Purifier；普通模板变量经 HTML 转义，可信 HTML 需显式标记。
- [网页安装](INSTALLATION.md)是一次性授权的新站点安装流程；开发环境的私有配置、运行数据和上传文件不进入 Git。上述措施值得保留，修改时须继续运行回归。

## 工程范式与推进顺序

现有项目保留了轻量路由、模型、模板和可定制字段，适合传统共享主机；代价是大量动态 SQL/DDL、字符串拼接和模板内 PHP 表达式使信任边界难以集中验证。建议先建立“控制器校验 → 领域服务 → 数据访问”的逐步迁移边界，不必一次性重写 CMS：新增代码使用参数化查询、严格标识符校验和明确结果类型；旧代码按高风险路径逐段替换。模板现有 `{$变量}` 调用方式可保留。

建议按节点推进并分别提交：

1. **灾备与数据完整性**：停用或隔离旧后台备份恢复，完成可验证的转储/恢复流程；给模型导入增加解析、预览、白名单和副本演练。
2. **安全边界**：完成历史富文本审计/迁移、配置预检查、应用层会话时限和 Apache 入口收敛；升级旧 jQuery 并审查 DOM 写入点。
3. **性能与结构**：用真实数据副本测搜索计划与 SQL 次数，再实现数据库层分页、索引及批量读取；规划 MyISAM/utf8mb3 迁移。
4. **持续验证**：将现有检查接入 CI，补充备份恢复、历史富文本、Apache 入口和大数据量场景的专门测试。每个站点仍需在自己的受控副本上验收定制代码、数据库和上传文件。
