## DB01：备份定义与数据不在同一个结构版本

**调用链：**后台创建备份或导入前自动备份 → `CmsBackup::create()` → `inspect()` 读取对象、DDL 和列类型 → 获取全表读锁 → 使用缓存 DDL，按 `SELECT *` 的实际列写 INSERT → 发布 SQL 与校验清单。检查与读锁之间没有结构协调或锁后复核。

**独立重放：**

1. 隔离表 `qa_a` 初始只有 `id,value`。另一连接持有该表写锁，启动真实备份任务。
2. 通过进程状态确认备份已经完成结构检查，正等待 `LOCK TABLES` 的元数据锁。
3. 持锁连接执行 `ALTER TABLE qa_a ADD new_value varchar(30)` 并填写值，再释放锁。
4. 备份正常返回成功并发布清单。解析后，其 CREATE 只有 `id,value`，INSERT 却包含 `id,value,new_value`。
5. 当前新结构下核验报“列结构与备份不一致”；将隔离表恢复成备份声明的旧结构后，仍报“备份行列不完整”。因此它不是单纯的“站点后来升级导致旧备份不能导入”，而是文件在创建时已经内部不一致。

该反例在 **MyISAM 和 InnoDB 表上分别重放成功**。生产请求是否恰好进入该窗口取决于调度；本轮通过合法数据库锁稳定扩大窗口，未测量自然发生率。测试使用真实 SQL 列变更，没有声称本轮通过后台字段按钮重放了这一备份窗口。

**影响：**用户获得带正确 SHA-256 和成功状态的备份，但它不能按自身结构恢复；同一实现也用于导入前的保护性备份。文件完整性校验不能发现这种逻辑不一致。

**修复与验收：**让备份与模型/字段等 DDL 共用结构协调机制，在读锁保护下重新读取或核对对象及列定义；发现结构漂移时重试完整快照或明确失败，不能发布旧定义配新行。重放上述两种引擎的交错，并核验每条行记录的列序列与本文件的 DDL 一致。新增/删除表、视图变更也应纳入正式回归；这几个扩展窗口本轮尚未逐个实测。

## DB02：导入期间没有覆盖所有写入者的停写屏障

**调用链：**[确认导入](../admin/app/controller/dbmanageController.php#L118) → 数据库级 `fengcms_import_*` 命名锁 → 核验结构 → 自动备份 → 逐表暂存 → 整体交换。普通内容写入使用[模型及记录锁](../admin/app/model/contentWrite.php#L39)，字段操作使用[模型生命周期锁](../system/common/model_schema.php#L43)，上传使用[账号和请求键锁](../system/common/upload_request.php#L67)，均没有参加导入互斥协议。最终结构核验在自动备份之前，之后未建立防止继续变化的边界。

**场景一，已确认编辑消失：**隔离草稿原题为 A；启动恢复含 A 的备份，在真实自动备份完成后暂停服务调用。此时通过正常编辑页取得签名并提交标题 B，HTTP **200、`status=y`**。继续导入，返回成功后查询数据库，标题为 A；检查刚才的自动备份，也只有 A。分别把内容表设为 **InnoDB、MyISAM**，两次结果相同。

这次丢失发生在自动备份之后，与管理员主动选择历史备份覆盖当前记录有区别：B 既收到保存确认，又不在本次承诺的回退副本里。

**场景二，字段配置与物理列分离：**在同一“核验与自动备份完成、暂存尚未开始”的屏障，通过真实字段保存接口新增 `brgallery`，HTTP **200、`status=y`**。继续导入成功，物理表仍有该列，`view_field` 中对应配置为 **0 行**：暂存表克隆了变更后的物理结构，而模块字段配置恢复为旧备份。说明只在点击确认时重新核验，并不能保护后续整个恢复过程。

**约束说明：**当前界面和文档明确要求“导入期间暂停内容写入”。严格落实外部停写可以避开本项；本报告不把“预览后修改记录，再主动恢复历史数据”本身列为缺陷。这里的问题是程序只有提示，不能拒绝仍在运行或排队的正常写请求，也未覆盖模型结构操作。若继续把外部停写作为强制前提，应提供可验证的维护流程，不能将现有导入锁描述为全站写入隔离。

**修复与验收：**在最终核验及自动备份之前建立跨请求的恢复屏障，先阻止新写入、等待已进入的写入完成，再保持屏障直至交换、校验及恢复状态落定。内容、栏目、模型/字段、上传及其他会修改被恢复状态的入口应使用一致协议，并设计与既有锁的固定顺序。并发写请求必须明确拒绝或排队后重新核验，不能先确认成功再静默丢失。正式验收重放上述两种引擎和字段窗口，另补上传与公开写入口；本轮未重放上传恰好跨越表交换的细分窗口。

## DB03：连接中断后的临时表没有可恢复的生命周期

**调用链：**随机生成 `cmsimp_*` / `cmsold_*` 名称，只存在当前 PHP 调用的数组中 → 使用导入连接创建暂存表 → 失败时在 `finally` 中继续用该连接 DROP。没有持久化操作清单，也没有下一次请求可安全核对的恢复入口。

**独立重放：**

1. 执行真实自动备份和逐表导入；另一连接在正式内容表持有事务元数据锁，使导入停在整体 `RENAME TABLE` 之前。
2. 对精确记录的隔离库导入连接执行 `KILL CONNECTION`，触发真实连接丢失；没有终止其他请求或服务。
3. 导入抛出 `MySQL server has gone away`。正式内容仍完整，但 **23 张 `cmsimp_*` 表残留**，失效连接无法完成清理。
4. 以原备份再次调用正式核验，因实际表集合多出临时表而失败，错误为“备份与当前数据库的表或视图不一致”。
5. 再创建一份正常后台格式备份，它成功收录了全部 23 张内部残留表。故障残留也进入后续备份对象清单。

**影响：**原数据在本次交换前故障中没有丢失，但正常后台恢复不能直接重试。后续备份也不再只包含站点正式对象，需要人工判断并处理残留，增加误恢复和错误删除风险。

**修复与验收：**为恢复操作持久化操作 ID、阶段、正式/暂存/旧表映射及所有权；连接丢失后允许新连接核对并完成安全清理或续做。备份遇到未完成恢复时应协调等待或明确拒绝。不要按名称前缀无条件删除或忽略表，尤其不能盲删可能承载唯一旧数据的 `cmsold_*`。重放连接丢失后，正式数据应完整，原备份应可在明确恢复步骤后重试，后续成功备份不得悄悄包含故障暂存对象。**交换后的进程终止与旧表回收失败尚待验证**，本轮不声称已覆盖。

## DB04：备份锁等待不受声明预算约束

代码设 `MAX_SECONDS=120` 并调用 `set_time_limit(130)`，但显式耗时检查要等阻塞的 `LOCK TABLES` 返回后才运行；新连接没有设置相应数据库锁等待上限。

**独立重放：**隔离连接持有目标表写锁，启动真实 `CmsBackup::create()`。数据库 `lock_wait_timeout` 为 **31,536,000 秒**；到 **132.11 秒**，任务仍在 `Waiting for table metadata lock`。释放阻塞锁后，约 **132.13 秒**才返回“备份超时”，未发布文件，临时文件已清理。

这是应用预算没有约束到阻塞 SQL 的实测；本次长等待使用容器内 CLI PHP，不据此推断所有共享主机的 FPM、代理硬超时均相同。外层请求超时也不能代替应用层可靠释放与错误处理。

**影响：**备份任务长时间占用进程和 `.backup.lock`，其他备份及依赖自动备份的导入不能正常开始。它不等于导入交换的元数据锁超时：后者本轮约 5 秒失败并清理，符合现有实现。

**修复与验收：**为数据库锁获取设置与剩余总预算一致的等待上限，将连接、预检、锁等待与导出统一计入期限；超时后释放数据库及文件互斥并清理未发布文件。在数据库支持范围内分别验证实际等待方式，不能仅增加循环中的时间判断。对持续持锁者重放，任务应在明确预算内结束且后续任务可正常开始。

配套文件演练使用真实带请求键的附件上传与正常内容保存：

- 原请求键和原字节仍具备时，再次上传可恢复原缺失路径。不能据此假定所有历史附件均有可用的原载荷。

这些结果符合[现有说明](DATABASE_IMPORT.md)中“数据库备份不包含上传、源码和私有配置”的边界，**不另外列为缺陷，也不据此重开 RA03**。完整恢复应在同一停写窗口取得数据库、上传、运行配置及对应代码/私密配置的配套快照；在副本恢复后验证引用和实际文件。该完整文件快照流程本轮未实现或生产演练。

## 实施顺序与验收要求

建议先处理 **DB02 的恢复停写边界及 DB01 的结构快照**，避免成功写入丢失和失效保护备份；再完善 **DB03 的持久化恢复状态**，并补齐 **DB04 的阻塞预算**。可共享协调机制，但每项应保留独立反例回归及故障后的重试验收。

继续保持认证、角色、POST/CSRF、预览与一次性 nonce、受限格式解析、确认时哈希和结构核验、导入前自动备份及整体交换。不能改回执行上传 SQL，也不能以取消结构核验、忽略未知表或删除上传文件来绕过上述问题。

本轮未覆盖 MariaDB 专项并发、锁权限缺失、真实磁盘耗尽、全部 SQL/文件 I/O 中断点、交换后强杀恢复及生产容量。这些均为**待验证**；既往功能回归通过不替代本轮新增失败场景。
