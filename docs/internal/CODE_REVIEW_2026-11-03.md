# FengCMS 代码审阅报告

日期：2026-11-03。源码基线：`486bb34`；开始审阅时工作区干净。本次仅新增报告，不修改业务代码、模板、页面样式或数据。

## 总体判断与范围

适合继续渐进整理，不建议整体重写框架或更换模板引擎。认证、CSRF、参数绑定、富文本清洗、模板可信 HTML 标记、上传校验、并发写入协调、编译缓存原子替换已经形成相当完整的基础。当前更值得投入的是：补齐旧辅助入口的边界，减少无意义的连接和缓存失效，把新增安全逻辑从历史通用函数中分离，并让注释与真实契约一致。

重点阅读了请求分派、公共安全函数、模型与 mysqli 驱动、模板编译和渲染、前台内容/搜索/栏目/留言、后台登录与内容写入、资源列表/缩略图/上传及富文本清洗。对相关回归和 CI 做了检查。配置、安装、数据库恢复及模型导入本轮仅查看结构和相关边界，未完成专项逐行审计；第三方源码、全部 JavaScript 与定制模板未逐一审阅。

维护记录只用作背景，以下结论以当前源码为准。没有把已经修复的循环重复求值、导航全表读取、相关文章无界搜索等问题重复列为现存缺陷。

### R01：图片列表可能包含未发布内容

位置：`app/model/moduleModel.php:164`，`pic()`。

条件只有 `img!=""` 和栏目约束，没有 `status=1`。因此调用该方法的定制模板可能获得草稿及回收站记录的标题、图片、链接；额外字段参数还会扩大返回字段范围。详情控制器本身的发布检查不能阻止列表提前展示这些字段。

无数据库探针直接执行原方法、替换数据访问并记录条件，得到 `img!="" and (classid=1)`，确认没有发布状态约束。该探针不代表真实 HTTP 数据泄露复现。仓库自带前台模板未发现调用，且此项曾在 2026-10-28 前台审阅中列为待验证，本次确认它仍未补齐。

建议：在内容图片查询内部明确发布规则，保持方法签名、字段及模板调用方式不变。需要同时检查是否存在将 `pic()` 用于非内容表的定制调用。增加草稿、发布、回收站各一条记录的回归，确保只有发布记录进入结果。

### R02：`l()` 的查询状态会跨调用残留

位置：`app/model/moduleModel.php:21,108`。

`tagsresolve()` 修改实例属性 `$op`，`l()` 开始时没有重置它。复现：在同一实例先调用 `l('article','w[status=1];n[1]')`，再调用 `l('article','')`，第二次仍携带 `status=1`；字段和排序同样可能残留。空参数只重置 limit，不能清除其他状态。

默认 `M()` 每次新建对象，常见的独立模板调用不会遇到此问题；保存模型实例并复用的 PHP 扩展或定制模板会受影响。

建议：每次解析使用独立选项数组，旧签名保留。回归覆盖复用对象的两次调用、字段/排序/条件分别省略及默认 limit。不要顺手改变通用 `model` 的全部查询状态语义，那需要独立兼容性评估。

### R03：全站聚合与停用模型规则不一致

位置：`app/model/moduleModel.php:346,362,381,400`，`wh()/wt()/wn()/wpic()`。

四个方法选择模型时只有 `type=1`，没有 `status=1`。虽然各分支过滤内容记录的发布状态，停用模型内已经发布的记录仍可能进入全站聚合；而内容详情、当前导航和搜索都要求模型启用。

自带模板未发现调用这些方法，不认定现有首页已经暴露停用内容。建议给这些内容聚合入口统一模型可见性规则，并覆盖停用/重新启用模型、零候选模型的回归。保留原方法名、返回字段、排序和去重语义，不直接把 `UNION` 改为 `UNION ALL`。

### R04：纯标签读取触发额外连接和缓存失效

位置：`app/model/moduleModel.php:325`；`system/core/model.php:359`。

`atags()` 使用默认 `excsql()` 执行固定的 `SELECT name ... WHERE name IN (...)`。该入口默认会隔离连接，并增加 `requestWriteRevision`。它没有声明为已经审查的只读查询，因此纯读取也会使栏目树、字段能力等依赖版本号的缓存失效；是否造成后续重读取决于本次渲染调用顺序。

此外，空字符串经过 `explode(',', '')` 得到包含空字符串的数组，仍会执行一次标签查询。

建议：在确认这里只访问预期实体表、没有状态型 SQL 表达式后，为这一调用使用现有只读路径；空标签走无查询返回分支，并保持原逗号与转义输出契约。不得把所有原生 SQL 的隔离默认值全局关闭。

验证：比较输出字节、连接数、SQL 数量，以及调用前后请求缓存版本。此轮确认的是额外工作路径，没有测得实际提速比例。

### R05：缩略图与上传的解码预算不一致

位置：`admin/api/thumbnail.php:10-12`；对照 `admin/api/upload.php:59-70`。

上传在 GD 解码前按剩余内存预算拒绝过大图片，缩略图接口只限制文件大小及 2,000 万像素，就直接读完整文件并解码。较低内存配置下，或面对旧站点导入的大图，仍可能发生预览失败甚至内存耗尽；`@` 不能把内存耗尽变成正常错误响应。

这是已认证接口的可用性加固项，不是已证明的匿名攻击入口。本轮未执行大图内存压力复现。

建议：提取共用图片检查/解码预算函数，上传与缩略图统一调用；按源图尺寸、文件字节和目标画布估算，超预算返回可处理的错误。不能只降低全站尺寸上限而不检查已有图片兼容性。

### R06：旧兼容入口仍有运行时诊断

位置：`app/model/moduleModel.php:33,81,346` 等。

- `module()` 使用未定义的 `$table`，并调用通用模型不存在的 `findall()`。探针首先复现 `Undefined variable $table`；后续方法不匹配由模型类接口确认。应明确查询 `module` 并使用实际存在的取数方法，或先确认没有外部调用再废弃。
- `tagsresolve()` 对 `s[id]` 直接访问 `$exp[1]`，探针复现 `Undefined array key 1`。这属于不完整模板参数的诊断缺陷，应明确拒绝或采用兼容默认值。
- `wh()/wt()/wn()/wpic()` 的 `$array` 未预先初始化，无符合条件模型时会读取未定义变量。建议初始化为空数组并定义空结果契约；本项为静态确认。

这些入口说明“PHP 语法全通过”不等于执行路径都无告警。应优先补实际契约回归，而不是再降低错误报告级别。

## 进一步的性能优化候选

以下不是已证明的生产瓶颈，应先测量再决定是否实施。

1. **资源列表扫描与缩略图缓存。** `admin/api/files.php:37` 起每次翻页均扫描目录、收集元数据并排序，之后才分页；分页减少响应体，不减少扫描工作。目前已有 10,000 项上限。先测典型大目录，再考虑短期目录索引；上传成功必须使索引失效。缩略图已有浏览器私有缓存，但跨浏览器或缓存过期仍重复解码；可考虑受控派生文件缓存、内容/版本键与容量清理，所有读取仍须先认证。
2. **内容页点击数写入。** `moduleModel::content()` 每次访问都执行点击数更新并取得数据库写入门锁。它还会增加请求缓存版本。在高并发和存量 MyISAM 表下值得单独测量，但不能直接移除备份/恢复屏障，或未经确认改为近似计数。可先研究按表/元数据类别区分缓存失效，保留未知原生 SQL 的保守策略。
3. **搜索统计与宽字段。** 当前 `searchPage()` 的指定模型查询使用 `*`，统计也包裹相同结果集。大正文和高命中查询值得测量执行计划、扫描行数、P95 与内存。不能仅为减少开销就改变跨模型去重、排序、总数或关键词匹配语义；普通索引也不能直接解决所有前导通配匹配。
4. **模板缓存检查。** 编译缓存命中时仍读源模板并计算内容摘要。它解决了保存时间戳精度问题，不能简单退回只比较 mtime。只有测出文件读取成本明显时，才考虑可靠版本标记，并保留外部文件修改、同秒修改及并发更新回归。
5. **清洗器定义缓存。** HTML Purifier 定义缓存目前关闭，实例仅在请求内复用。若测得初始化占比明显，可以研究私有运行目录中的定义缓存；必须隔离不同规则版本，并保持 vendor 目录只读。不要跳过服务端清洗或直接信任所有历史 HTML。

不建议先上整页缓存：当前页面包含会话 CSRF 信息、动态阅读数等，必须先定义可缓存内容和会话隔离。也不建议在没有代表性数据时批量添加索引。

## 代码组织与注释建议

### 保留所有外部契约，先整理内部职责

- `system/common/security.php` 同时承担会话、身份、角色、路由表、分类权限、HTML 标记、路径及参数处理。可按职责分为会话认证、授权路由、输入校验、输出与路径工具，原文件保留兼容加载入口。分拆前先列清独立 API 和主应用各自的加载顺序，避免循环依赖。
- `app/model/moduleModel.php` 混合标签表达式解析、列表查询、搜索、详情组装与 HTML 生成。可逐步提取内部服务，原 `M('module')` 及公开方法继续作为适配层；已经存在的 `CmsSearchCriteria`、`CmsPageContext` 是可沿用的方向。
- 后台内容保存已经提取 `ContentWrite`，值得继续沿这条路径整理，而不是重新把锁、幂等、业务校验堆回控制器。下一步可把 `_write_token`、`_create_key` 和账号上下文显式传给内部服务，兼容入口负责读取全局请求。
- 新代码优先使用数组条件与参数绑定。历史字符串 `where/field/sort/limit/alter` 是受信任代码接口，必须标明禁止直接接收外部输入；本轮未确认它们形成新的可利用 HTTP SQL 注入链，不能仅凭拼接就标为漏洞。

### 注释应描述真实契约与原因

`system/core/model.php` 的 `insert()` 注释写 `bool|void`，实际返回插入 ID 或 false；`update()` 实际返回影响行数或 false，零行并不必然表示保存失败。`M()/D()` 的注释参数也与真实签名不一致，前台多个模型仍写“首页模型”。这些误导比缺少作者横幅更值得修正。

建议优先补充：参数类型与数组结构、返回值与失败方式、是否持锁/写会话/失效缓存、富文本信任前提、MyISAM 与事务差异。删除失效的注释代码和“读取配置”式重复描述时按模块小步处理，保留必要版权声明。新增说明以中文为主，技术标识保持原名；不要为翻译注释修改第三方源码。

### 类型与静态检查逐步收紧

模型基类仍有 `AllowDynamicProperties`、隐式属性和混合返回值。先补准确 PHPDoc、明确 `$name` 等核心属性，再给新增内部服务添加类型；不要直接移除动态属性兼容层或全仓添加严格类型，定制扩展可能依赖旧行为。

CI 已具备 PHP 8.4/8.5 集成回归及 PHP 诊断门槛，可以增加只覆盖自有代码、针对未定义变量/不存在方法/错误返回注释的渐进静态检查。现存告警应有明确基线，不通过大范围忽略规则掩盖。格式调整与行为修复分开提交，避免全仓格式化干扰历史追踪。

## 安全方面应保留的设计

- 保留服务端角色、POST/CSRF、账号指纹与会话有效期；不能用 UI 隐藏替代授权。
- 保留上传 MIME、扩展名、尺寸、实际解码与目录不可执行约束；网络图片保持浏览器引用。
- 保留默认模板转义及 `CmsHtml` 显式信任标记，`cms_html()` 不是清洗器。
- 在线模板编辑属于超级管理员受信任代码能力，不建议在保持现有函数/表达式语法的同时声称它是安全沙箱。
- 动态 URL 编译保护目前有特定语法匹配范围，如双引号中的单变量 href。定制模板的单引号属性、混合表达式、内联 JavaScript 仍需按输出上下文审阅；HTML 转义不等于所有上下文安全。本轮没有证明具体新增 XSS 链，不作漏洞定性。

## 建议执行顺序与验收

1. 先修 R01/R03 可见性、R02 状态残留、R06 旧入口；每个关键节点独立回归、独立提交。
2. 再修 R04，核对 HTML 输出、连接数与缓存版本；R05 单独验证低内存、大图和损坏图片。
3. 选择有代表性的隔离数据测量性能候选，记录数据量、冷热缓存、SQL 数、扫描行数、中位数、P95、峰值内存，避免以少量本地请求承诺提速比例。
4. 最后按触及模块整理注释、类型与文件职责，保持 URL、模板语法、输入字段、富文本存储及视觉结果。

这些改进不要求修改 `{$变量}`、`{$record['fy']}`、`{loop ...}`、`l(...)` 等模板写法。可见性修复会排除本就不应发布的数据，这是安全边界修复，不是页面设计调整。
