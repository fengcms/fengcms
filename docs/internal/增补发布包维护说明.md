# 增补发布包维护

使用 `./bin/package-release v1.38 v1.37` 同时生成完整 ZIP、增补 ZIP、独立 SHA-256 和 SHA256SUMS.txt，产物在忽略目录 var/releases。必须先提交全部修改并创建对应正式标签，两个标签的 admin/version.php 要与标签一致，基准必须是目标祖先，不能相同。

bin/package-upgrade 通过 git archive 获取两份正式发布树，继承标签自身的 export-ignore。按路径比较字节和权限，重命名表现为删除旧文件及新增新文件；普通变更位于“网站文件”，服务器配置位于“服务器配置参考”。所有删除仅生成中文清单，不自动执行。清单携带前后摘要与提交，避免仅凭版本号判断定制是否可覆盖。

验证器读取实际 ZIP 载荷和模式，按清单在内存叠加基准树（服务器配置按参考文件合并后的目标内容模拟），处理删除后与完整目标树逐项比较，拒绝缺失、额外载荷及摘要/权限不一致。人工服务器配置合并与定制冲突仍须由站点维护者解决；打包一致性不等于生产升级成功。

发布前下载并验证 GitHub 已发布基准 ZIP，与其正式标签文件树核对。测试 tests/package-upgrade-regression.py 覆盖新增、删除、重命名、权限变更、配置分离、叠加及异常路径/载荷。v1.37 → v1.38 明确无新增数据库迁移；今后版本不能据此推断，应更新发布说明和包内指引。

顺序：本地适用回归 → 分节点提交 → 最终版本标签打包验证 → 推送最终提交与标签 → 等待 GitHub static 及 PHP 8.4/8.5 integration 全部成功 → 再发布 Release 并上传全部校验产物。CI 失败时修复并重新验证，不降低诊断门槛。不要强行移动已经对外发布的标签；发布前若需修正本地或未发布标签，也应先审视远端状态。
