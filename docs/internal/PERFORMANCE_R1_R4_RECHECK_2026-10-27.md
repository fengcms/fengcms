## R1 原生 SQL 默认隔离已替代首词识别

主要修复提交：`fcff584`、`93f6859`。相关后续调用调整：`87ed0d0`。

[query()](../../system/core/model.php#L376)在执行原生 SQL 前直接切换至模型独立连接；[excsql()](../../system/core/model.php#L359)默认采用相同策略。原先依赖语句首词识别会话操作的正则已移除，因此前置注释不会使原生事务落回普通共享连接。

`excsql()` 的第三个参数允许经审查的纯读取显式复用连接。这是内部调用契约，不是对任意 SQL 的自动安全判定。本轮核对的[搜索调用](../../app/model/moduleModel.php#L253)使用程序构造的查询、绑定参数和普通列名判定；自定义字段表达式仍走默认隔离路径。

### 独立重放上次失败用例

在带开发标记的数据库中建立独立随机前缀的 InnoDB 测试表，用不同模型执行事务插入和普通插入，再回滚事务。通过读取驱动连接 ID 检查连接归属，没有先调用可能改变连接归属的默认原生读取接口。

| 事务开始形式 | 两模型连接不同 | 事务内插入被回滚 | 普通插入保留 |
| --- | --- | --- | --- |
| `/* followup probe */ START TRANSACTION` | 是 | 是 | 是 |
| `-- followup probe` 换行后 `START TRANSACTION` | 是 | 是 | 是 |
| `# followup probe` 换行后 `START TRANSACTION` | 是 | 是 | 是 |
| `/*!80000 START TRANSACTION */` | 是 | 是 | 是 |
| `BEGIN` | 是 | 是 | 是 |
| `START TRANSACTION` | 是 | 是 | 是 |

[原生 SQL 独立回归](../../tests/raw-sql-isolation-regression.php)也已通过，额外覆盖带注释的用户变量设置、会改变会话状态的 `SELECT`、临时表与连接级锁。原来的跨模型回滚问题未再复现。

## R2 事务结束后缓存能够刷新

主要修复提交：`54a75c3`，并与后续原生 SQL 隔离调整共同生效。

[affairs()](../../system/core/model.php#L420)在 `COMMIT` 和 `ROLLBACK` 成功执行后更新请求修订号；默认原生 SQL 执行后也保守更新修订号。[栏目快照](../../app/model/classifyModel.php#L51)改用普通模型查询，避免读取快照本身经由默认原生 SQL 触发额外失效。

### 独立重放上次失败顺序

使用独立随机前缀的 InnoDB 栏目测试表，保持上次“提交前先读取一次缓存”的关键顺序：

1. 读取初始导航。
2. 独立事务更新栏目名称，暂不提交。
3. 普通读取取得旧值并建立当前快照。
4. 提交事务后再次读取导航，再用独立数据库连接核对实际值。

| 读取位置 | 上次结果 | 本次结果 |
| --- | --- | --- |
| 初始导航 | `before_commit` | `before_commit` |
| 事务未提交时导航 | `before_commit` | `before_commit` |
| 事务提交后导航缓存 | `before_commit` | `after_commit` |
| 事务提交后数据库 | `after_commit` | `after_commit` |

本次缓存与已提交数据库值一致。[事务缓存回归](../../tests/cache-transaction-regression.php)还覆盖 `affairs()` 提交与回滚、`query('COMMIT')`、`excsql('COMMIT')`、字段能力缓存及普通更新，均通过。

这里验收的是请求内缓存一致性。原生 SQL 的保守失效可能增加快照重建，应在后续代表性性能测量中继续观察，不把一致性修复本身解释为已经证明查询次数最优。

## R3 实际 Fatal 和解析错误可触发诊断失败

主要修复提交：`86181b1`。

[诊断汇总](../../tools/summarize-php-diagnostics.py#L12)已支持 Warning、Deprecated、Notice、Fatal error 和 Parse error，能够处理 Fatal 首行的 `文件:行号` 及后续 `thrown in` 行；没有已知位置的诊断也会计入，而不是静默忽略。

本次既运行 `python3 tests/php-diagnostics-regression.py --live-php`，又独立重放了上次的真实异常探针：通过模型非法标识符校验触发未捕获异常，在建立数据库连接前终止，再将实际 stderr 输入汇总脚本。

| 观察项 | 上次结果 | 本次结果 |
| --- | --- | --- |
| PHP 异常进程退出码 | 255 | 255 |
| 诊断脚本退出码 | 0，漏报 | 1，正确拒绝 |
| 诊断计数 | 0 | 1 |
| 汇总输出 | 无有效诊断位置 | `Fatal error` 与应用文件行号 |
| 异常消息原文 | 未输出，但 Fatal 漏报 | 本次断言确认汇总未输出 `Invalid SQL identifier` |

退出码 255 和 1 是此负例的预期结果，包裹它的验证命令成功结束。标准日志回归另覆盖多行 Fatal、首行无位置而后续补充位置、Parse error 以及普通诊断；多行 Fatal 计数为一次。真实 Fatal 核验已加入 [CI 集成任务](../../.github/workflows/verify.yml)。

## R4 模型导入已在消费 nonce 后释放会话

主要修复提交：`13bd307`。

[loading()](../../admin/app/controller/modulemanageController.php#L143)先检查预览和 nonce，删除 `model_import_preview`，再调用 `cms_session_release()` 持久化消费结果，最后进入实际模型导入。认证及 POST/CSRF 守卫继续由原路由流程执行。

本次运行了[HTTP 回归中的真实模型导入并发用例](../../tests/regression.php#L726)。该用例只在带开发标记的本地数据库中短暂锁住模型表，使导入停在数据库等待阶段，在释放数据库锁前检查同会话的其他请求：

| 场景 | 本次结果 |
| --- | --- |
| 导入到达可观测的数据库等待状态 | 通过 |
| 同会话资源列表请求 | HTTP 200，等待期间已完成，未超时 |
| 同会话再次确认相同 nonce | HTTP 400，等待期间已拒绝，未超时 |
| 释放数据库锁后的原导入 | HTTP 303，预期的新模型创建成功 |
| 已成功导入的 nonce 再次使用 | HTTP 400 |
| 导入失败后访问资源列表 | HTTP 200，会话仍有效 |
| 导入失败后的 nonce 再次使用 | HTTP 400 |

这次验证包含实际 HTTP、真实导入和数据库等待，不再只依赖 `session_status()` 的模拟检查。它证明了该入口在所测环境中的会话释放和一次性消费行为，不代表所有导入规模或共享主机配置的吞吐量测试。
