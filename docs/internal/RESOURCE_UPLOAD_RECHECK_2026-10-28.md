## RA01：图片实际解码

源码链路：文件大小、扩展名、实际 MIME 与尺寸检查 → [内存预算及 GD 实际解码](../../admin/api/upload.php#L60) → [保存文件并返回 URL](../../admin/api/upload.php#L79)。无法解码或解码尺寸不一致时，在进入最终存储前返回错误。原大小及像素上限仍在；成功校验不重编码文件。

独立重放使用与原报告相同结构的 PNG：合法签名、IHDR、文本与结束块，但缺少像素数据。确认它仍能通过 `finfo` 与 `getimagesize()`，且 GD 解码失败；正常认证和 CSRF 的 multipart 请求返回 **400**，未生成对应最终文件或上传状态记录。截断 PNG 同样被拒绝。

被拒绝的尝试不会占用请求键：随后使用同键上传合法 PNG 成功，取回字节与原文件完全一致。正常 640×480 图片可生成 320×240 缩略图；带脚本样文本注释的合法 GIF 及普通附件也保留原字节。原来的坏资源 URL 已无法由该上传路径以成功结果产生，RA01 可以关闭。

限制：此次独立重放不是全部格式、所有损坏形态或生产并发容量测试。内存预算是按像素和文件大小估算，未测得所有解码器的原生内存峰值；较低内存限额可能提前拒绝接近尺寸上限的合法图片，开发方已在升级说明中记录。

## RA03：同次上传的结果恢复

源码链路：队列项生成随机请求键，重试[沿用该键](../../admin/js/resource-picker.js#L190) → 上传适配器提交 `_upload_key` → 服务端按账号和键取得[数据库命名锁](../../system/common/upload_request.php#L67) → 核对目录及文件名、大小、内容哈希 → [先持久化目标随机路径](../../system/common/upload_request.php#L82) → 移动或校验已有文件 → 更新完成状态 → 返回 URL。

独立 HTTP 重放结果：

| 场景 | 本次实测结果 |
| --- | --- |
| 完整发送 multipart，关闭连接且不读取响应 | 首次完成状态及实际文件均存在；同键原载荷重试为 200、原 URL、相同哈希，匹配文件数为 1。 |
| 只发送部分请求体后断开，再同键重试 | 中断时无最终文件、无状态记录；重试正常生成一份资源。 |
| 两个并发请求使用相同键和原载荷 | 两者均为 200、同一 URL，实际只有一份文件。 |
| 同键更换文件名或内容 | 返回 409，不被当作原请求成功结果。 |
| 目标已移动但状态仍为 pending | 同键重试返回原 URL，并完成原记录。 |
| 已记录的目标文件缺失 | 同键原载荷重试恢复原路径及字节，再返回成功。 |
| 已记录目标的字节被改变 | 返回 409，不覆盖已改变的文件。 |
| 用户以新键主动再上传相同文件 | 得到新 URL，两份文件；保留主动重复上传的现有语义。 |

另外在独立库对上传状态表设置临时触发器，令“移动成功后的完成状态 UPDATE”真实抛出 SQL 错误。第一次返回预期的 **500**，文件存在且原记录保持 pending；解除故障后同键重试返回 **200 和原 URL**，状态变为 complete，匹配文件仍为一份。这与单纯手工设置 pending 的检查分开执行，验证了真实失败后的恢复。故障触发器只存在于本轮隔离库。

原结果不确定重试已获得稳定操作身份及可恢复路径，RA03 可以关闭。此结论适用于当前客户端保留请求键的同次操作：不带键的旧客户端仍使用随机新路径；超过 30 天的状态记录可被低频清理，不承诺旧键永久幂等。刷新页面后另起上传也不等同于原队列项重试。
