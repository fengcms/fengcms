# 数据库恢复复查遗留问题修复

依据[DB01–DB04 复查报告](DATABASE_BACKUP_RECOVERY_RECHECK_2026-10-28.md)，DB01 与 DB04 已关闭；本轮处理 DB02、DB03 共同的交换后断线窗口。

## 修复规划与结果

1. **延长停写边界至待恢复状态结束。** 普通写入取得数据库槽位后、进入业务逻辑前检查私有恢复记录。这样排队请求即使在导入连接断线后才取得槽位，也会返回 409。后台内容和模型结构、前台 POST、浏览计数及独立上传共用此检查。登录、只读页面和受保护的恢复操作保留可用。所有入口统一读取后台私有备份目录，避免前台与独立 API 指向不同目录。
2. **防止旧版本已确认编辑被静默丢弃。** 在整体交换前，为每张暂存表记录列元数据和全部行的顺序无关 SHA-256 指纹。交换后、`committed` 标记前发生中断时，恢复逐表对比当前正式表；不一致或旧记录缺少指纹时，拒绝自动回退，保留当前正式表、旧表及恢复记录，要求先保全并人工核对。交换前中断仍可清理本次登记的暂存表；已提交阶段仍只清理登记的旧表。
3. **验证并按节点提交。** 隔离库真实终止交换后的导入连接，覆盖排队写入、MyISAM 与 InnoDB 内容、结构修改、旧版已确认编辑、恢复后的重试；主 HTTP 回归覆盖独立上传、登录和只读入口。

## 验证

- `./bin/dev check`：PHP 8.4.27，349 个文件，无语法错误。
- `./bin/dev test`：主回归 602 项通过；隔离导入、备份一致性和 MyISAM 结构回归通过。专项在真实 `RENAME TABLE` 完成后的核对阶段终止连接，确认排队写入与后续写入被拒绝；模拟旧版已确认修改后恢复拒绝自动回退；未修改时恢复、重新预览、导入和后续写入均成功。
- 独立上传通过有效 PNG 的实际 HTTP 请求验证待恢复时返回 409，无文件及上传请求记录；登录与只读页面保持可用。测试使用私有隔离库与已标记的开发数据，待恢复记录及临时表已清理。

## 操作边界

若恢复提示“正式数据已变化或缺少核对记录”，不要强制删除恢复记录。先取得数据库及上传文件的配套快照，在独立副本比较正式表与登记旧表，再决定保留或合并。系统不会自动合并冲突数据。插件、外部脚本和数据库客户端如果绕过 CMS 写入槽位，必须由站长另外暂停。仍待专项演练：进程或主机强杀、磁盘耗尽、MariaDB 并发和各类虚拟主机的权限与超时。
