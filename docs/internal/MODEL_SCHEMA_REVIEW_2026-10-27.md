## MS01 新增字段失败后遗留孤立列

**位置与调用链：**`fieldmanage&operate=save` → [新字段校验及建列](../../admin/app/model/fieldmanageModel.php#L175) → 第 190 行 ALTER TABLE → 第 191 行写入 `module_field`。新增分支先改变物理结构，随后直接插入配置，没有补偿或恢复处理；重试只检查字段配置是否存在。

**独立复现：**

1. 通过后台接口创建临时模型，新增文本字段 `f_fault`。
2. 在该字段的配置 INSERT 处注入 SQL 异常。
3. 请求返回 500；物理列已经存在，但对应配置为 0 行。
4. 移除故障后原样重试，仍返回 500：配置检查认为字段未创建，随后再次 ADD COLUMN 撞上已有列。

另直接 POST 一个 51 字符的别名，在本轮严格模式下同样返回 500，并留下有列无配置的状态，不需要测试触发器。该载荷绕过了浏览器中的长度提示，说明服务端尚未在建列前验证配置列长度；这不是声称正常浏览器表单允许提交该长度。

**影响：**用户无法从失败响应判断物理变更已经发生，字段列表又没有可操作的配置记录；修正输入后重试仍失败，需要人工核对表结构。

**修复要求：**先对白名单配置、类型和实际存储长度完整校验，再执行 DDL。在模型结构互斥范围内记录操作归属和阶段；配置写入失败时，要么安全撤销本次新建且未被使用的列，要么保留明确的恢复状态并可继续补齐配置。不能仅根据“配置不存在”认定物理列也不存在，不能为清理失败请求删除其他操作创建或已经存有数据的列。

**验收：**超长配置在 DDL 前拒绝且列不出现；受控配置 INSERT 失败后，结构与配置一致，或有可识别的待恢复状态；解除故障后原请求可安全完成，不发生重复列、重复配置或误删已有值。

## MS02 删除字段失败后无法对齐物理结构与配置

**位置与调用链：**[字段删除控制器](../../admin/app/controller/fieldmanageController.php#L105)先调用 [fielddel](../../admin/app/model/fieldmanageModel.php#L46) 删除物理列，再删除配置行。第二步失败时第一步已经不可回滚；重试又无条件 DROP COLUMN。

**独立复现：**创建自定义字段 `f_del`，在临时内容行中保存 `original-value`，仅在该字段配置 DELETE 处注入异常。删除返回 500，物理列已经不存在，配置仍保留 1 行。移除异常后重试删除，因列不存在再次返回 500，配置仍未清理。两个元数据引擎均复现。

**影响：**一次显示失败的删除实际上已经移除字段及其值，却保留可见的失效配置，正常重试无法结束。字段值删除本身是这次请求的预期破坏性动作；问题在于失败状态和实际完成阶段不一致，不能把 500 理解为数据仍保留。

**修复要求：**定义删列与删配置的恢复契约，持久记录已经执行的阶段，重试时核对实际列状态并继续完成剩余步骤。如果承诺可撤销，必须在 DROP 前具备可恢复的数据副本或采用分阶段保留方案；仅加事务不能恢复已经删除的列值。删除操作还需确认字段归属及其是否允许删除。

**验收：**在配置删除阶段失败后，响应能表明已完成的破坏性阶段；移除故障后重试可得到一致的最终状态。已不存在的列不能成为永久卡住配置清理的原因，也不能误删同名的新字段。

## MS03 系统字段批量添加遇到复合列冲突后部分完成

**位置与调用链：**[systemsave](../../admin/app/model/fieldmanageModel.php#L214)整批校验字段类型 ID，但没有整批检查将要创建的物理列；[属性字段映射](../../admin/app/model/fieldmanageModel.php#L312)一次创建 `attrib_j` 等六列，已有字段判断却只看配置中的逻辑名称 `attrib`。

**无需故障注入的复现：**

1. 新建临时模型，通过自定义字段接口正常创建名为 `attrib_j` 的文本字段。
2. 系统字段批量提交 `record=['2','3']`，即“栏目”“属性”。
3. 请求返回 500；`classid` 的物理列和配置均已创建，属性 ALTER 因已有 `attrib_j` 失败，`attrib` 配置不存在，其余属性列也未创建。
4. 原样重试仍返回 500，没有交付已完成项与失败项明细。

两个元数据引擎下结果一致。此场景没有直接修改业务表来制造列冲突，两个步骤均走受支持的后台接口。

**影响：**输入类型合法仍会在执行中出现部分完成，用户只能看到整体错误；继续重试不能解决冲突，且逻辑字段与复合物理列的命名约束缺失。

**修复要求：**为系统字段维护完整物理列映射，处理自定义字段与系统保留名称的冲突。在任何 DDL 前核对整批计划、现有列及其定义，并选择明确契约：发现冲突整批拒绝，或交付逐项完成、失败和未处理结果及安全重试方式。不能把 ID 合法校验等同于结构预检完成。

**验收：**重放上述两个正常请求，不得再发生只有 500 的隐式部分完成；已有 `attrib_j` 的定义和值须保留。重复选择、已完整存在的复合字段、只有部分物理列存在及中途 SQL 失败都应有一致结果。

## MS04 模型删表后配置删除失败无法恢复流程

**位置与调用链：**[模型删除](../../admin/app/controller/modulemanageController.php#L68)顺序为 DROP TABLE → 删除模型行 → 删除字段配置，没有分阶段恢复，也没有在重试时识别已经缺失的表。

**独立复现：**通过正常接口创建模型并写入一条临时内容，仅在模型配置 DELETE 处注入异常。删除返回 500，物理表已不存在，模型行仍有 1 条、默认字段配置仍有 7 条。移除异常后重试，先前的 DROP 已无法再次执行，请求继续返回 500，剩余配置仍未清理。两个元数据引擎均复现。

**影响：**后台留下看似存在但无法使用的模型，常规删除入口无法继续清理。与 MS02 一样，删表是用户发起的破坏性操作；失败不代表原表仍在，也不能靠回滚配置事务恢复表内容。

**修复要求：**为模型删除建立可恢复阶段和明确的结果，重试可识别本次已删除的表并完成剩余清理。删表前完成引用预检，恢复或重试必须核对模型身份，避免项目代号已被新模型复用时误删新表。若提供撤销，应在破坏性 DDL 前准备实际可用的快照。

**验收：**分别在删表后、模型行删除后、字段清理阶段注入失败；每种状态都能查询实际进度并安全完成或恢复。只剩配置的模型不应永远卡在 DROP 不存在表的错误上。

## MS05 正常删除模型遗留栏目与内容状态

**位置与调用链：**[模型删除](../../admin/app/controller/modulemanageController.php#L72)仅清理物理表、模型行和字段行，没有检查或处理 `classify`、`content_recycle_state`、`content_create_request` 的关联。后续 [栏目删除](../../admin/app/controller/classifyController.php#L138)仍会访问已删除模型的内容表。

**无需故障注入的复现：**为临时模型增加栏目字段，创建本模型父栏目及 `article` 模型子栏目，正常新增一篇内容并回收，然后删除临时模型。

| 核对对象 | 删除后的实际结果 |
| --- | --- |
| 模型、字段配置、内容表 | 已删除，HTTP 200。 |
| 父栏目与跨模型子栏目 | 仍有 2 条，父栏目继续引用已不存在的模型。 |
| 回收前状态 | 遗留 1 条。 |
| 新增幂等请求记录 | 遗留 1 条。 |
| 再通过正常栏目接口删除父栏目 | HTTP 500，因访问已不存在的内容表失败，父栏目仍保留。 |

两个元数据引擎均复现。内容状态残留在本轮仅确认其未清理，不据此声称已发生新模型误还原或重复创建。

**影响：**模型删除成功后仍留下不可正常管理的关联结构；父栏目失效还会牵连其他模型的子栏目。状态记录持续残留，模型代号复用时的归属边界也未由删除流程处理。

**修复要求：**明确模型删除的引用契约。可以在仍有栏目引用时拒绝删除并列出引用，也可以设计有预览和明确确认的级联方案，但不能默认为应连带删除其他模型的内容。清理或保留状态记录时应绑定明确的模型身份与生命周期，纳入同一可恢复流程。

**验收：**覆盖无引用、只有本模型栏目、跨模型子树、回收记录和新增请求记录。删除被拒绝时不得先 DROP；允许删除时不得留下引用失效模型的栏目及无归属状态。其他模型的内容不能被未经明确约定的级联误删。

## MS06 模型生命周期操作缺少统一互斥

**位置与调用链：**[模型导入](../../system/common/model_package.php#L180)持有按数据库和项目名计算的命名锁，但[普通模型删除](../../admin/app/controller/modulemanageController.php#L68)不取得该锁。内容编辑使用[记录与栏目关系锁](../../admin/app/model/contentWrite.php#L95)，模型删除也不参与这些保护。

### 导入与删除交错

使用正常导出的模型包和两个独立超级管理员会话。在导入已建表、已插入模型行、准备插入首条字段配置的位置，由隔离库测试触发器设置最多 20 秒的等待屏障；另一会话通过正常删除接口删除这个已经可查询的模型。删除中的部分 SQL 也可能等待，屏障退出后两个流程继续交错完成。

本轮完整专项运行观察到：删除 HTTP 200；导入 HTTP 303，跳转到 `imported=1`；最终内容表与模型行均不存在，但遗留 **3 条字段配置**。残留数量取决于交错顺序，问题判定依据是孤立配置不为零，以及导入结束时没有核对模型完整性。

导入自身的命名锁没有阻止删除入口访问同一模型。这不等于所有引擎都会出现完全相同的交错：本次该时序在新安装的 InnoDB 元数据表上验证，没有把它外推为 MyISAM 下同样残留 3 条。

### 已进入保存流程的内容编辑与模型删除交错

正常加载内容编辑签名，在记录命名锁处阻塞真实保存请求，确认它已经读完字段并进入锁等待；另一会话删除模型，返回 200。释放记录锁后，旧保存访问已不存在的内容表，返回 500。该请求已经通过入口处的模型存在检查，删除时没有等待它完成，也没有让它在继续保存前得到明确的模型冲突结果。

作为对照，同样的内容编辑等待期间只删除一个自定义字段，释放锁后旧编辑返回 409，原标题未被覆盖；现有编辑签名能够保护该行形状变化，不能把所有结构并发都判定为失效。

**影响：**导入可能报告成功却留下无归属配置，模型删除与在途请求之间没有一致的完成顺序；入口校验通过后仍可能变为缺表错误。

**修复要求：**统一模型新增、导入、结构变更、删除与内容操作的生命周期协调机制，规定锁顺序和删除状态。取得保护后重新确认模型身份及结构，模型未完整初始化时不能作为可删除或可写的正常模型公开。删除应与正在执行的操作形成可解释的先后顺序或返回明确冲突；导入发布成功前需保证表、模型行和字段配置齐全。跨模型栏目操作也须纳入锁顺序设计，避免引入死锁。

**验收：**独立会话重放导入各阶段与删除交错，全部结束后孤立字段应为 0，成功状态应符合确定的执行顺序；覆盖内容保存已过入口校验后发生的模型删除。还应覆盖删除后同项目名重建，确保旧请求和旧清理不会作用于新模型。

## 正常路径与现有保护

本轮没有把以下通过的行为列为问题：

- 模型正常创建、导出，以及经新预览重新提交的模型导入成功。
- 在导入字段写入处注入 SQL 异常后，导入器清理本次表、模型行和字段配置；旧 nonce 再次提交返回 400，重新预览后可导入。
- 重复创建已有项目返回已有提示，原内容保留；两个独立会话同时普通创建同一项目，只发布一个模型，本轮结果分别为 `y`、`n`。
- 两个独立预览同时导入同一项目，HTTP 结果为 303、400，最终只有一个模型；此时双方均经过导入器自身的互斥。
- 字段编辑只允许展示元数据变化，伪造列名、类型和所属模型没有改变物理身份。这一页面没有承诺支持物理类型或列长度修改，本轮不把未提供此能力认定为缺陷。
- 删除自定义列后旧内容编辑返回 409，没有覆盖原标题。

本轮未进行生产操作、进程强杀或数据库连接中断恢复演练，没有测量大表 ALTER 的停写时长、磁盘耗尽或生产吞吐量，也没有重做真实浏览器整页交互。上述六项是本轮确认的问题；这些未覆盖情形仍待独立验证，不能由本地 HTTP 和受控 SQL 异常结果推定通过。
