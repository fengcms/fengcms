## TC01 设置保存失败仍改变 URL 模式

**数据流：**表单 `url_type` → 同目录临时 JSON → [rename 发布 `site.json`](../../admin/app/model/baseModel.php#L68) → 更新 `f_base` → 返回保存结果。文件发布先于 SQL，失败没有回补或可恢复状态。

**独立重放：**先正常保存网站名称 A、标题 A、动态 URL 模式 0。给隔离设置表加入仅对本轮标记名称生效的 `BEFORE UPDATE` 触发器，真实抛出 SQL 错误；再通过正常接口提交新名称、新标题和模式 1。

InnoDB、MyISAM 两次均得到 **HTTP 500**，数据库名称和标题仍为 A，`site.json` 却已经是模式 **1**；下一次前台请求为 200，实际显示旧名称与新 `URL_TYPE=1`。移除本轮触发器后重试，才能重新得到配套状态。

**影响：**用户收到保存失败，却已有部分设置生效，可能改变全站链接行为。这里不是配置文件损坏：JSON 完整，问题在一次保存缺少跨存储的提交边界。

**修复与验收：**定义统一、可恢复的设置发布协议；失败不应留下未说明的部分配置。协调同一站点的并发保存，不能只把 SQL 放入事务，也不能简单交换写入顺序。失败回补不能覆盖另一请求已成功发布的版本。正式回归重放 SQL 失败及文件发布失败，覆盖两种引擎，核对失败后的全部设置、前台实际模式和重试结果。

## TC02 设置旧表单覆盖新保存

**独立重放：**两个管理员分别通过真实设置页面读取相同的名称 A。管理员一修改名称并保存，接口确认成功；管理员二仍使用旧页面的名称 A，只修改描述后提交。第二次也返回 **200、`status=y`**，最终数据库为旧名称 A 加新描述，第一次确认的名称修改消失。

保存实现没有比较打开编辑页时的版本；页面的时间字段也没有作为并发条件使用，服务端直接写入当前时间。该问题不需要两个 SQL 同时执行，只要编辑会话重叠就能发生。

**修复与验收：**让编辑页携带服务器认可的版本基线，并在提交的同一个互斥/条件更新步骤中核验。失配应明确提示冲突并保留输入，不能静默覆盖。基线应同时考虑本次设置的文件状态，避免只保护数据库字段；仅使用秒级时间戳不足以区分同秒多次保存。重放双管理员、同秒保存及失败后的重试。

## TC03 模板旧版本与同名重建未隔离

两个真实模板编辑页都读到 `TITLE=V0 / BODY=V0`。管理员一改 TITLE 并收到成功；管理员二从旧页面只改 BODY，仍提交原 TITLE。第二次成功后，文件为 `TITLE=V0 / BODY=ADMIN_B`，管理员一的修改丢失。

另在管理员一保持旧编辑页时，管理员二通过实际接口删除文件，再以同名新建不同内容。管理员一提交旧表单，仍返回成功，新建内容被旧版本覆盖。对照测试中，文件删除且尚未重建时，旧保存返回 404，因此现有检查保护的是“路径是否存在”，并没有保护正在修改的资源版本。

当前同目录临时文件加原子 rename 能保证读到完整文件，但不能解决旧内容覆盖新版本。

**修复与验收：**在读取时提供内容/版本基线，在互斥发布步骤中核对后再替换；删除和同名重建也要参加一致的版本协议。版本冲突应保留用户输入并明确拒绝。保留新建时硬链接发布的同名保护、空文件支持、权限及路径限制；不要退回直接覆盖写入。正式回归覆盖两个编辑页、删除后保存、删除重建后旧保存，以及 CSS/碎片等共享该实现的类型。

## TC04 编译失败与清理竞态产生旧输出或空白成功

编译器的 `wfile()` 会返回失败，但调用方[不检查结果就返回编译路径](../../system/core/template.php#L180)；渲染器继续 include。缓存清理直接递归删除目录，与编译发布及打开产物的生命周期没有共同协调。

**确定性故障：**

1. 正常渲染模板 A，使编译文件存在；通过实际模板接口保存 B，收到成功。
2. 仅将隔离编译目录设为不可写，再请求前台，返回 **HTTP 200 和旧模板 A**，新 B 没有显示。
3. 移除本轮旧编译产物，保持目录不可写，再请求，返回 **HTTP 200、正文 0 字节**。
4. 恢复本轮目录权限后，请求正常显示 B。

**真实并发：**在多进程 HTTP 服务中，交错发起 **240 次前台请求和 30 次实际清缓存 POST**，出现 **33 次 HTTP 200、正文 0 字节**。清理响应中 27 次提示成功、1 次失败、2 次提示已经更新。服务日志有编译文件不可用及 include 的 Warning；本地绑定挂载还出现 `Stale file handle`。结束后正常渲染恢复。

这是一组本地受控样本，不是生产故障率或容量结论；其他文件系统需单独复测。确定性权限故障与并发清理分别执行，未把两者混成同一注入。

**修复与验收：**检查编译和发布结果，失败必须进入明确的失败或有定义的降级路径，不能返回空白成功。让渲染持有可用产物直至执行完成，清理不能删除尚待打开的当前产物；保留完整文件原子发布。错误详情留私有日志，向用户返回受控状态。验收应重放暖/冷缓存写入失败，以及并发渲染、编译和清理，断言状态码与正文完整性，不只检查“请求没有 Fatal”。

## TC05 清缓存覆盖范围及状态判断不完整

**仅一侧存在：**先正常预热前后台缓存，第一次清理成功，两侧目录消失。测试不跟随结果页的后台跳转，先访问前台使其重建，再发清缓存请求：响应提示“缓存已经更新”，但前台编译文件仍在。原因是入口要求两侧目录同时存在，否则完全跳过清理。

为检查实际生效，另在隔离模板中模拟部署保留旧修改时间：源码为 B、编译产物仍为 A。上述单侧清理后仍显示 A；重新建立后台缓存，使两侧目录存在再清理，才正常显示 B。

**移动端遗漏：**在隔离副本建立移动模板目录，以实际 iPhone User-Agent 请求，确认使用 `compile_mobile`。更新移动模板为 B 并保留较早时间戳，预热前后台桌面缓存后执行正常清理，响应提示成功，移动缓存却仍存在并输出 A。只移除本轮对应移动编译文件后，请求立即显示 B，说明新模板本身有效。

**修复与验收：**按实际配置逐个处理前台、后台及启用的移动缓存目录，缺少一侧不能跳过另一侧。使操作幂等，提示应反映真正清理或失效的范围，并与 TC04 的并发读写协议配合。回归覆盖两侧存在、任一侧缺失、移动目录启用、重复请求及保留时间戳的发布。仅扩大删除范围而不处理 TC04，可能让渲染竞态更频繁。
