## R1 前置 SQL 注释绕过事务连接隔离

优先级：**P1，阻断整体完成验收**。关联原项：PERF02。涉及提交：`8b7c50e`、`f8d6d2c`。

### 代码证据

[isolateForSessionSql()](../../system/core/model.php#L380)只匹配语句开头的空白与 `BEGIN`、`START TRANSACTION`、`SET` 等关键字。合法的前置 SQL 注释不在匹配范围内。因此：

```sql
/* followup probe */ START TRANSACTION
```

会继续在普通共享连接上执行，而不是切换到独立连接。[query()](../../system/core/model.php#L368)和 `excsql()` 都依赖这项识别。

### 已复现行为

在带开发标记的数据库中建立独立、随机前缀的 InnoDB 测试表，两个模型使用相同配置。按以下顺序操作，表名仅作示意：

```php
$transaction = D('probe');
$ordinary = D('probe');
$transaction->query('/* followup probe */ START TRANSACTION');
$ordinary->insert($fixtureRow);
$transaction->query('ROLLBACK');
```

实际结果：两个模型仍使用同一个连接，普通模型的插入被另一个模型的回滚撤销。预期结果：事务模型独立，普通模型的正常提交不受它的回滚影响。

这是模型原生 SQL 接口的兼容性回归，不是对现有 HTTP 页面已经丢失数据的断言。触发前提是调用者通过该接口执行带前置注释的事务语句；当前新增回归只覆盖无注释的事务和 `SET`。

### 修正要求与复验

- 明确原生 SQL 的连接隔离策略，不能只通过当前首词正则宣称所有会话级操作都已隔离。
- 覆盖普通块注释、行注释以及 MySQL 可执行注释；同时核对临时表、用户变量和连接级锁等会话状态的归属。
- 至少补上上述跨模型回滚用例，确认普通写入保留、事务内写入回滚、连接 ID 符合隔离约定。
- 对无注释 `BEGIN`、`START TRANSACTION`、`SET` 及 `affairs()` 保留现有回归，避免修补识别后退化已有路径。

## R2 独立事务提交后栏目缓存仍返回旧值

优先级：**P2，缓存一致性验收未通过**。关联原项：PERF03，并影响采用相同修订号机制的缓存。

### 代码证据

模型写入时递增请求修订号；[栏目 snapshot()](../../app/model/classifyModel.php#L51)据此刷新快照，但快照查询使用普通共享连接。独立事务尚未提交时，该连接只能读到旧的已提交值。

[affairs('commit')](../../system/core/model.php#L427)仅执行 `COMMIT`，不更新修订号。如果事务未提交时恰好刷新过快照，提交后修订号不再变化，旧数据会继续被当作当前快照。[字段能力缓存](../../app/model/moduleModel.php#L421)也使用这一修订号机制，应一并检查。

### 已复现行为

使用独立随机前缀的 InnoDB 栏目测试表，调用真实的前台栏目模型与模型事务接口：

1. 读取导航，栏目名为 `before_commit`。
2. 独立事务将栏目名更新为 `after_commit`，暂不提交。
3. 再读取导航，此时读到 `before_commit`；该旧值被缓存到新的修订号下。
4. 提交事务，再读取导航，并通过另一数据库连接核对实际值。

| 读取位置 | 实际值 |
| --- | --- |
| 事务前导航 | `before_commit` |
| 事务未提交时导航 | `before_commit` |
| 事务提交后导航缓存 | `before_commit` |
| 事务提交后数据库 | `after_commit` |

事务未提交时读取旧值本身符合隔离语义；问题是提交后同请求的后续读取仍无法刷新。开发记录中“模型写入后请求内快照失效”的表述尚未覆盖这一过程。该复现使用 InnoDB，不将结果外推为现有所有表都具备相同事务行为。

### 修正要求与复验

- 将事务提交、回滚与读取缓存的失效时机纳入统一约定；区分写入执行成功和对其他连接可见。
- 同时覆盖 `affairs()` 及原生 SQL 接口的事务结束路径，避免只修一个入口。
- 补充“写入后、提交前读取缓存，再提交再读取”的回归；事务提交后必须看到新值。
- 覆盖回滚、普通非事务更新，以及栏目快照和字段能力缓存；不得缓存跨连接不可见的数据状态。

## R3 PHP 诊断门槛漏报实际 Fatal 日志

优先级：**P2，CI 验收未通过**。关联原项：CODE03。涉及提交：`cd9f193`。

### 代码证据

[诊断脚本的正则](../../tools/summarize-php-diagnostics.py#L13)要求同一行同时出现 `PHP Fatal error:` 和 `in /var/www/html/... on line N`。

PHP 未捕获异常的实际日志通常在首行使用 `文件:N`，在后续行使用 `thrown in 文件 on line N`。两行各自缺少当前正则所要求的一部分，导致诊断计数为零。[CI](../../.github/workflows/verify.yml#L39)依赖这个脚本的退出码判定失败。

### 已复现行为

通过真实模型构造器的非法标识符校验触发未捕获异常，将 PHP 实际 stderr 输入现有脚本。该探针在数据库连接建立前即终止，没有执行数据库写入。

| 输入或执行 | 实际结果 |
| --- | --- |
| 普通 Warning 日志对照 | 脚本退出码 1，计数 1 |
| 实际 PHP 未捕获异常 | PHP 退出码 255，stderr 包含 Fatal 及应用文件位置 |
| 上述实际 stderr 输入诊断脚本 | 脚本退出码 0，计数 0 |
| 合成的标准 Parse error 日志 | 脚本退出码 0，计数 0 |

Parse error 的结果来自日志格式用例；Fatal 的结果来自实际 PHP 运行输出。`./bin/dev check` 仍能捕获其扫描范围内的语法错误，但不能因此把运行期日志门槛认定为完整有效。已有 Python 回归仅验证了普通 Warning，没有覆盖这些格式。

### 修正要求与复验

- 支持未捕获异常的多行 Fatal 格式，合理归并同一个错误的首行和 `thrown in` 行，避免重复计数。
- 将 Parse error 纳入诊断分类，或明确建立单独且有效的失败机制。
- 保留路径及行号汇总，不在报告输出中泄露异常消息、输入值或凭据。
- 为正常日志、Warning、Deprecated、Notice、实际 Fatal、多行栈和 Parse error 增加对照测试，核对退出码及脱敏结果。

## R4 模型包导入执行仍保持 Session 文件锁

优先级：**P2，原优化项尚未覆盖的路径**。关联原项：PERF04。这是源码确认的收尾项，不是本次新引入的数据错误。

[modulemanageController::loading()](../../admin/app/controller/modulemanageController.php#L143)校验并删除 `model_import_preview` 后直接执行 `CmsModelPackage::import()`。这一 POST 路径没有调用 `cms_session_release()`，也不经过 GET 渲染释放逻辑，因而会在导入期间继续保持文件会话锁。

数据库备份导入已经在消费 nonce 后释放会话，模型包导入尚未做同样处理。开发记录中的“导入已释放”需要限定为实际覆盖的入口。

### 修正要求与复验

- 在认证、CSRF 和导入 nonce 校验完成、预览状态消费并持久化后，再进入耗时导入。
- 用独立会话验证一个模型导入请求与另一个同会话请求可以在耗时阶段并行。
- 验证两个竞争请求不能重复消费同一个 nonce，导入成功与失败路径都不会丢失必要会话状态。
- 本次没有执行真实模型包导入的并发演练；下一轮必须补充这项验证，不能仅以 `session_status()` 的模拟测试替代。
