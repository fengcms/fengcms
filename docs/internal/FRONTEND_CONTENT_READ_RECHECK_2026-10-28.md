## 逐项复验

### FR01：停用模型栏目访问 — 关闭

`classifyController::ensureEnabledModelCategory()` 在动态和伪静态路由解析后执行，并要求对应 `project` 存在 `type=1 AND status=1` 的模型，否则返回 404（`app/controller/classifyController.php:34,56,59-64`）。栏目树快照与导航查询也增加了启用模型过滤（`app/model/classifyModel.php:82-93`；快照逻辑见同文件）。实现覆盖了原报告中的栏目路由与导航/地图不一致场景。

修复记录称回归包含动态、伪静态栏目和导航/地图用例；本次未重跑测试，运行时结论以开发方记录为辅，源码防护路径已确认。定制模板直接使用低层模型辅助方法读取内容的行为不在本次路由门禁覆盖范围内；如部署依赖此类模板调用，仍应单独核查。

### FR02：相关文章自身与顺序 — 关闭

`moduleModel::related()` 从请求的 `project/id` 识别当前文章，将其从候选集合排除，并在最终查询中按 `id DESC` 排序（`app/model/moduleModel.php:431-454`）。当前模板继续使用原有 `related(project,tags)` 调用，因此不需要改变模板接口。新增回归测试源码断言不包含当前记录且结果顺序稳定（`tests/frontend-content-read-regression.php`）。

该排序把 ID 作为近期顺序代理；若业务要求严格按发布时间排序，应另行定义排序契约，但这不影响原报告中“自身可能入选、没有稳定顺序”的问题已解决。

### FR03：相关文章扫描上界 — 未关闭

修复将标签输入限制为最多 8 个、每个最多 64 字节，并只对最多 500 个候选 ID 执行原有子串 `LIKE`；这确实限制了 LIKE 分支数量及其匹配集合（`app/model/moduleModel.php:420-454`）。但候选发现查询本身是 `status=1 [AND id<>?] ORDER BY id DESC LIMIT 500`（同文件 `438-443`）。`LIMIT 500` 只限制返回数，不保证执行时最多检查 500 行。

默认文章表具有 `(status,id)` 索引（`install/install.sql:1-26`），但自定义模型表是受支持的数据模型。模型包导入创建表时只加 `PRIMARY KEY(id)`（`system/common/model_package.php:212-225`），导出格式也拒绝除主键外的索引（同文件 `79-82`）。因此，对合法自定义模型，数据库可能沿主键检查大量行以找到 500 条已发布记录；若已发布记录稀少，扫描量可随表增长。新增回归夹具显式建立 `KEY status_id(status,id)`（`tests/frontend-content-read-regression.php:12`），没有覆盖上述自定义模型结构。

**关闭条件：**在隔离库对默认文章表及无 `(status,id)` 索引的合法自定义模型分别执行 `EXPLAIN ANALYZE`，覆盖已发布行稠密与稀疏情况；证明候选阶段的实际检查行数有可接受上界，或调整实现/模型索引契约后补充相应回归。现有修复将匹配窗口限定为 ID 最新的 500 条，旧内容可能不再出现在相关结果中；此兼容性取舍已在修复记录披露。

### FR04：导航数据库工作量 — 未关闭

导航查询现在按父栏目直接执行 SQL 并应用 `nav=1`、排序及 limit，避免将完整栏目树读入 PHP（`app/model/classifyModel.php:82-100`）。但是默认 `f_classify` 只有主键，没有 `classid/nav/sort` 辅助索引（`install/install.sql:86-107`）。导航对根级及展示父级逐次调用该查询；缺少适配索引时，每个查询仍可能扫描并排序大部分栏目表。返回条数被 limit 限制，不代表数据库检查行数或排序工作量被限制。当前分类回归对查询次数/结果的断言不能替代执行计划和扫描量验证。

**关闭条件：**对真实默认表结构及代表性大栏目数据采集导航查询的 `EXPLAIN ANALYZE`，检查 examined rows、排序/临时表以及根级和子级累计查询开销；根据证据增加兼容的索引/采用批量取数策略，并覆盖栏目增删改后的升级和回归。现阶段可以确认 PHP 侧全树构建已移出普通导航路径，但不能确认整体数据库负载已得到有界控制。
