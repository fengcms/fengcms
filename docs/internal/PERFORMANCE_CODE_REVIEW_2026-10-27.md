## PERF01 模板循环对数据表达式求值两次

### 证据与影响

[模板编译器](../../system/core/template.php#L220)的两种循环规则均将数据表达式写入 `is_array()` 和 `foreach()`：

```php
if (is_array(expression ?? null)) {
    foreach (expression as $item) {
        // 循环正文
    }
}
```

当 `expression` 是 `l(...)` 或模型方法调用时，会重复执行查询及结果处理。[首页模板](../../template/index.html#L38)多处直接循环查询结果，因此该成本存在于正常页面调用链中。变量数组本身的二次读取不等于二次查询，不能把所有循环都计为重复 SQL。

使用实际编译器编译下列探针，数据函数返回 `['a'=>1,'b'=>2]` 并记录调用次数：

| 输入模板 | 数据函数调用次数 | 渲染结果 |
| --- | --- | --- |
| `{loop review_loop_items() $item}{$item}{/loop}` | 2 | `12` |
| `{loop review_loop_items() $key $item}{$key}{$item}{/loop}` | 2 | `a1b2` |

### 优化要求

编译时先将数据表达式求值一次，再判断类型并遍历。为各层循环生成独立临时变量，避免与业务变量、嵌套循环和包含模板发生冲突。更新编译器后确保已有编译缓存会刷新。

### 验收标准

- 两种循环语法的数据表达式每次进入循环结构时只求值一次；空数组也只求值一次。
- 空值和非数组继续跳过循环；键值、顺序和正文输出保持一致。
- 覆盖嵌套循环、相同业务变量名、包含模板及条件内循环。
- 在固定数据下比较首页、栏目页及内容页的输出和 SQL 次数；只减少重复工作，不改变记录数量、排序及可见性。

## PERF02 数据库连接反复建立与站点设置重复读取

### 证据与影响

[模型构造器](../../system/core/model.php#L59)将 `$classname` 设为字符串后调用 `is_object()`，这个判断不能实现连接复用。每次构造模型都会创建新的驱动对象。[M 和 D 工厂](../../system/common/function.php#L64)每次也都会创建模型实例。

本地验证确认：连续两次 `D('base')` 持有不同的 MySQL 连接；`M('module')` 本身同样建立连接，而其列表等方法随后又使用 `D(...)` 执行查询。PERF01 的重复求值会进一步放大连接开销。

[首页控制器](../../app/controller/homeController.php#L15)两次调用 `M('web')->information`，[首页模板](../../template/index.html#L1)又调用一次；[web 模型](../../app/model/webModel.php#L17)每次构造都会读取基础设置。版权清洗已有请求内及可选 APCu 缓存，不能据此声称清洗每次都重复执行，但基础设置查询仍然重复。

### 优化要求

普通同配置查询可按请求共享数据库连接，查询构造对象保持独立。明确连接所有权和关闭时机，避免临时模型析构时关闭仍被其他模型使用的连接。不要仅将 `$classname` 改成对象判断，也不要直接缓存带有查询条件的模型来代替连接管理。

备份、导入、事务和会话级 SQL 配置需要独立评估，不能为了连接数将它们无条件合并到普通查询连接。保持参数绑定、字符集设置、受影响行数及新增 ID 的语义。首页直接复用已取得的站点设置；扩大缓存范围时再设计失效规则。

### 验收标准

- 普通同配置查询在同一请求内复用连接；不同配置及明确要求独立连接的操作可以隔离。
- 两个模型的条件、字段、排序及分页不会相互污染。
- 一个模型销毁或关闭后，仍存活模型的连接行为符合明确约定。
- `affected_rows()`、`insert_id()` 及异常处理通过回归；备份与导入的锁、事务和 SQL 模式语义保持一致。
- 固定页面记录优化前后的连接建立次数、SQL 次数和响应时间，避免只统计模型对象数量。

## PERF03 栏目数据重复查询与建树成本

### 证据与影响

存在三种不同的重复工作：

1. [前台栏目模型](../../app/model/classifyModel.php#L50)使用实例属性 `$childMap` 缓存栏目索引，但 [whereclass()](../../app/model/moduleModel.php#L191)每次通过 `M('classify')` 创建新实例。多个内容区块无法共享已有索引，仍可能反复读取整张栏目表。
2. [导航模板](../../template/scrap/header.html#L79)先读取顶级栏目，再[逐父栏目读取子栏目](../../template/scrap/header.html#L129)，查询次数随展示的父栏目数量增长。
3. [后台 classifytree()](../../admin/app/model/classifyModel.php#L110)在每次递归时扫描完整输入数组。对于全部可达的 N 个节点，遍历比较次数为平方级；它不是数据库 N+1 查询，而是内存建树算法的问题。

前台已有一次读取加索引的实现，不能沿用早期报告将其描述为完全未优化的递归查询。

### 优化要求

提供请求内共享的栏目数据与父子索引，按用途生成导航、后代列表和栏目路径；后台建树使用父 ID 索引，避免每个节点重新扫描完整数组。先实现请求内复用，再考虑跨请求缓存，避免同时引入失效策略的复杂度。

### 验收标准

- 同请求多次读取相同栏目快照时不重复全表读取；同请求修改栏目后不会继续使用过期快照。
- 栏目数量增加时，导航不再逐父节点新增查询，后台建树趋于线性遍历。
- 保留 `sort,id` 等原有顺序、外链及单页行为、隐藏状态和现有层级语义。
- 覆盖空栏目、深层栏目、孤立节点及循环父子关系，保证可终止且结果符合明确约定。
- 请求内共享数据不得串用前后台权限、数据库或表前缀不同的结果。

## PERF04 Session 文件锁阻塞并行请求

### 证据与影响

[应用入口](../../system/app.php#L34)统一启动 Session，[会话初始化](../../system/common/security.php#L4)使用 PHP Session 接口。本地容器处理器为 `files`；当前主要页面保持会话到请求结束，[缩略图接口](../../admin/api/thumbnail.php#L5)已有提前关闭的示例。

在独立临时会话中，一个进程持锁约 300ms，第二个进程访问同一会话等待约 288ms，两进程均正常结束。这证明当前处理器的同会话锁行为，不代表生产页面的具体延迟或吞吐量。不同会话不由这把锁彼此串行化。

### 优化要求

按接口盘点最后一次会话写入位置，在认证、CSRF 校验及所需状态写入完成后释放锁，再执行耗时查询或文件处理。搜索频率窗口、验证码、登录退出、导入预览 nonce 等仍有会话写入，必须逐条核对；不能在所有入口启动会话后立即统一关闭。

### 验收标准

- 两个同会话请求在进入可并行的耗时阶段后，不再被 Session 锁串行阻塞。
- 关闭后的会话写入不会静默丢失；会话过期和账号失效校验仍按每次请求生效。
- 搜索限流、验证码消费、登录退出、CSRF 及导入预览状态通过回归；竞争请求的最终状态有明确约定。
- 独立验证目录和会话文件在完成后清理，不使用真实用户会话做测试。

## CODE01 查询统计污染后续查询状态

### 证据与影响

[getcount()](../../system/core/model.php#L103)把 `$this->options['field']` 直接替换为统计表达式。用查询记录器执行同一对象的 `where(['status'=>1])->getcount()`，随后调用 `getall()`，两条 SQL 均为：

```sql
select count(id) from review_rows WHERE `status` = ?
```

这确认统计操作会影响后续字段选择；不代表所有现有页面都已经出现错误，因为大量调用每次创建新模型。若后续直接复用模型，该隐含状态会更容易暴露。

### 优化要求

统计使用独立字段表达式或在操作后恢复原字段。先明确各查询方法对条件、字段、排序、分页和参数的保留规则，再做模型复用。另需核对[标签解析模型的 `$op` 状态](../../app/model/moduleModel.php#L101)：连续调用时应明确本次未传选项是否继承前次，不能在优化过程中无意改变旧模板语义。

### 验收标准

- 默认字段下先统计再取列表，列表仍读取正常字段；显式选定字段时能够保留原选择。
- 连续两次统计不会生成嵌套的 `count(count(...))`。
- 数组条件、原始条件加参数、排序及分页的参数数量和值保持正确。
- 多个查询对象之间不共享可变查询条件；同一对象的连续调用行为形成测试与文档约定。

## PERF05 搜索查询的重复计算与字段成本

### 证据与影响

[search()](../../app/model/moduleModel.php#L201)已经通过数据库 `LIMIT` 分页，不再使用旧报告所述的 PHP 全量分页。但是统计和列表分别执行带搜索条件的查询，跨模型使用 `UNION`，指定模型时选择 `*`，模型字段能力也逐模型检查。

实际成本取决于模型数量、数据规模、字段大小、查询命中率及执行计划。`LIKE '%关键词%'`、去重和排序可能成为成本来源，目前不能给出已确认的瓶颈排名或提速比例。

### 优化要求

按[性能测量计划](PERFORMANCE_MEASUREMENT_PLAN.md)采集统计与列表 SQL 的执行计划和基线，再评估字段裁剪、元数据批量加载、去重必要性、索引及更适合的搜索方式。修改 `UNION` 语义或查询结构前先确定跨模型结果的身份、排序和分页规则。

### 验收标准

- 覆盖指定模型、全站搜索、空结果、高命中、跨模型及边界页码。
- 列表、总数、稳定排序和发布状态过滤保持一致；模型字段差异得到正确处理。
- 记录扫描与排序情况、SQL 次数、峰值内存、响应时间中位数和 P95。
- 使用固定且有代表性的数据复测；没有可复现收益时不合入结构性优化。

## CODE02 请求与业务和渲染的职责交叉

### 证据与影响

[display()](../../system/core/controller.php#L35)在渲染前向 `$_GET` 填入默认值，页面渲染会改变全局请求状态。模板直接执行模型查询，例如导航和标题；[后台控制器](../../admin/app/controller/moduleController.php#L210)直接逐条操作数据库；[内容保存模型](../../admin/app/model/moduleModel.php#L66)又直接读取 `$_GET['project']`。

这些调用依赖使参数来源、查询次数和返回契约难以局部理解，也增加了独立测试与数据复用的成本。当前默认值处理承担旧模板兼容职责，不能直接删除后把 Warning 重新带回页面。

### 优化要求

选择一个模块试点，将校验后的请求参数明确传给业务方法，由业务层提供页面数据。模板及旧方法通过兼容入口继续工作，逐步收敛重复查询。统一响应辅助方法，减少散落的 JSON、内联脚本和跳转拼接；后台执行结果继续使用已有 `FengAdmin.executionURL` 约定。

### 验收标准

- 新业务方法可在不构造全局请求的情况下测试，参数及返回类型有明确约定。
- 迁移路径上的渲染不再改变原始请求参数；旧模板依赖的默认值由兼容层提供。
- 原路由、模板变量、普通值转义和可信 HTML 行为保持一致。
- JSON 和执行结果页的成功、失败、缺失 ID 及批量操作行为通过现有回归。
- 单次提交聚焦一个模块，避免同时重写框架和批量改动业务模板。

## CODE03 规范与测试组织及 CI 门槛

### 证据与影响

现有代码存在缩进混用、遗留注释代码、宽泛 PHPDoc 和未明确的参数及返回契约。例如 [display()](../../system/core/controller.php#L22)标注返回字符串，实际主要输出页面；通用模型和业务模型的职责也不一致。

仓库[已有 CI](../../.github/workflows/verify.yml)，覆盖依赖来源、前端回归、PHP 语法及 HTTP/数据库回归；不能表述为没有自动验证。但 [PHP 诊断汇总](../../tools/summarize-php-diagnostics.py#L12)只打印统计，不因新增 Warning 或 Deprecated 返回失败。主要综合回归集中在[大型脚本](../../tests/regression.php)，共享夹具与清理逻辑较多。

### 优化要求

先为新增和修改代码建立格式规则、准确的 PHPDoc、明确属性及返回契约，再逐步引入静态检查。按模块拆分综合回归，保留公共请求助手和可靠的夹具清理。为 PHP 诊断设置明确门槛；需要基线时记录允许的来源与收敛计划，避免全局屏蔽。

不要把全仓格式化、全量增加严格类型和业务性能修改混在同一次提交。历史扩展入口、动态模型和模板调用须核对兼容性，不能只为通过静态检查删除功能。

### 验收标准

- 格式与静态规则可以在本地和 CI 使用同一入口执行，并有明确检查范围。
- 新增诊断能使检查失败；既有允许项有可核对的范围，不依赖笼统忽略。
- 拆分后的模块测试能单独运行，完整执行覆盖不减少，异常路径仍清理自己的夹具。
- 纯格式提交不夹带行为修改，业务提交保留适用的语法、导航与集成验证。
