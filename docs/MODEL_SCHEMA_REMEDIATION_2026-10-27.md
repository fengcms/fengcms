# 模型结构一致性修复方案与实施记录

依据 [模型与自定义字段结构审阅](MODEL_SCHEMA_REVIEW_2026-10-27.md)，覆盖 MS01–MS06。日期：2026-10-27。

## 实施顺序与契约

1. **MS06 生命周期协调。** 按数据库和项目代号使用与模型导入相同的 MySQL 命名锁。普通模型创建、修改、导入、删除、字段结构修改及内容写入都在该锁内完成。内容写入顺序为模型锁、记录或创建请求锁、全局栏目关系锁；模型删除顺序为模型锁、全局栏目关系锁。导入和创建先以内部状态 `-2` 登记，字段配置齐全后才发布正常状态。
2. **MS04、MS05 删除。** 删除前在栏目关系锁内检查该模型的全部栏目引用，包括跨模型子树中的节点。有引用即返回 409，不删表、不级联其他模型内容。允许删除时先记录模型 ID 和操作阶段，再删表，清除字段配置、回收前状态和新增请求记录，最后删除模型行。任何阶段失败后以原模型 ID 重试；待恢复日志阻止同项目代号被重新创建或导入。栏目新增也在同一关系锁内核对模型是否存在且已发布，防止删除后新增悬空引用。
3. **MS01、MS02 自定义字段。** 在建列前校验服务端配置长度与系统保留列。新增和删除以模型 ID、字段 ID／名称及阶段记录在 `model_schema_operation`；重试时核对归属和物理列状态，再继续剩余步骤。若待恢复建列的定义已改变，或已完成删列后同名列再次出现，拒绝自动处理并要求人工核对。删除字段的物理值一旦 DROP 即不可撤销，失败响应明确指出物理列是否已经删除。
4. **MS03 系统字段批量。** 先展开整批物理列（属性字段映射为六列），检查列冲突，再执行任何 DDL。执行途中失败时返回已完成、失败、未处理明细；当前字段保留恢复日志，原请求可重试。已有物理列且没有本系统恢复日志时拒绝覆盖。
5. **验证。** 使用真实后台 HTTP、两会话和开发库临时模型复现拒绝、失败后重试、项目代号复用及保存与删除交错。应用语法检查、全套回归与后台回调测试。

## 数据库升级

`tools/migrate.php` 新增幂等的 `migrate_model_schema()`，新安装 SQL 同步创建 `model_schema_operation`。**部署代码前先运行迁移**；该表应保留 InnoDB，即使历史模型与字段元数据仍为 MyISAM。升级旧站须先备份数据库与上传文件，在副本演练，再安排结构变更维护窗口。MySQL DDL 已生效后无法靠事务还原字段值或已删除的表；恢复日志负责识别阶段与安全续做，不等于数据快照。

## 已执行验证

- 本地 Docker PHP 8.4 的 `./bin/dev check`（345 个 PHP 文件，0 个语法错误）、`./bin/dev test`（复审补丁后 587 项主回归通过）；主 HTTP/数据库回归覆盖新增字段 INSERT／DELETE、模型 DELETE、恢复日志 DELETE 的受控故障与重试，以及内容保存和模型删除、模型导入和删除的两会话交错。
- 系统字段整批预检、复合列冲突与值保留、批量中途配置失败及原请求重试；新增字段配置超长在 DDL 前拒绝。
- 正常删除被跨模型栏目引用的模型时返回 409，且保留表与栏目；解除引用后的模型删除会清除字段、回收状态和新增请求状态。重建同名项目后，旧模型 ID 的删除请求不会作用于新模型。
- 受控触发器只在本地开发库的临时测试窗口存在。`compose.yaml` 的测试库允许创建这些触发器；这一设置不属于生产部署要求。
- `tests/model-schema-myisam-regression.sh` 创建独立临时库、执行共享安装 SQL、仅将模型／字段／栏目元数据转换为 MyISAM，再验证字段增删故障续做、系统字段冲突预检、栏目引用拒删与模型删除重试；测试后撤销授权并删除整个临时库。

开发库的 HTTP 回归覆盖当前 InnoDB 元数据；独立 CLI 业务层回归覆盖历史 MyISAM 元数据及相同 DDL/恢复代码。后台结果回调的 288 种组合检查通过。MyISAM 路径没有重复完整 HTTP 身份、CSRF 与两会话时序，因这些入口在 InnoDB HTTP 回归验证。原浏览器后台会话已过期，未完成手工整页交互复验；生产大表 DDL、磁盘耗尽与进程强杀也未在此次自动化范围内。

## 运维边界

栏目仍引用模型时，应先核对栏目和其他模型的子节点，再通过明确的栏目管理操作处理，之后重试模型删除。故障后的 `model_schema_operation` 行包含原模型 ID、字段 ID、物理名称和阶段；不得直接清空该表后重用项目代号。字段与模型删除若已完成物理 DROP，恢复流程只续做配置及状态清理，不承诺恢复原数据。全局栏目关系锁和模型锁会让并发后台写入等待；大表 DDL 的停写时间需在站点副本测量。

## 复审补丁：排队保存与部分删除

[复审报告](MODEL_SCHEMA_RECHECK_2026-10-27.md)指出，删除已 DROP 表但模型行清理失败时，排队的旧内容保存可在取得模型锁后继续读取缺失表。现在单条保存、批量新增及 `ContentWrite` 写入在模型锁内统一核对原模型 ID、状态、待恢复操作和物理表；未发布、待删除或缺表状态返回 409，原模型仍可按原 ID 续做删除。

正式 HTTP 回归使用两个独立后台会话和测试触发器，在删除写入日志前设屏障，确认旧保存已排队等待模型锁，再令删除于删表后失败。验证删除与旧保存均返回 409、模型状态为 -2、表缺失而恢复日志保留；解除故障后原 ID 删除可完成。隔离 MyISAM 元数据回归另验证部分删除状态下单条保存、批量新增及直接写入均在访问缺失表前返回 409。生产环境、磁盘故障及进程强杀未在本轮验证。
