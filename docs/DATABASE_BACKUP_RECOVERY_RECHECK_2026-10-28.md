## 独立重放方法

使用随机命名、带 `f_dev_meta` 标记的隔离库，通过本仓库初始化与迁移函数建立完整 CMS、临时管理员和草稿；备份使用独立私有目录。HTTP 请求经过真实登录、会话、CSRF、编辑签名和导入 nonce。未回灌现有开发库或生产库。

需要精确调度时，直接调用真实导入服务已有的 `beforeStage` 回调，在真正的自动备份完成后设置测试屏障，再从另一请求访问正常业务接口。HTTP 恢复按钮、重新预览及确认导入另通过实际路由执行。没有修改业务方法或伪造 SQL 返回结果。

原交换前中断在 23 张正式表的夹具上重放。交换后直接中断的演练额外使用 70 张空夹具表，合计 93 张，仍在 100 表导入限制内，用于增加交换后核对阶段的观察窗口。它不改变 PHP 实现，也不是生产吞吐量测试。

## DB01 关闭证据

[备份协调入口](../system/common/backup.php#L102)现在先取得写入屏障；[取得读锁后](../system/common/backup.php#L152)和[导出结束前](../system/common/backup.php#L185)均重新检查对象、DDL 和列定义。

对 MyISAM、InnoDB 隔离表分别重放：先由另一连接持有写锁，待备份进入 `LOCK TABLES` 等待，再由持锁连接加列、填写值并释放锁。两次均报“数据库结构在取得读锁前发生变化”，没有新增成功备份。随后按新结构正常备份，解析得到的 DDL 列序列与行列序列相同，正式核验通过。

另外在同一等待窗口新建表、新建视图，备份均失败且未发布。当前失败信息为新增对象未被 `LOCK TABLES` 锁定；本轮确认的是安全拒绝，不将该错误文案评价为用户体验改进。

原来的“旧定义配新行并发布成功”已经消除，DB01 可以关闭。绕过 CMS 协议的外部写入仍需按[现行导入说明](DATABASE_IMPORT.md)另行停写。

## DB03 交换前中断已可恢复

在整体交换前，以事务元数据锁阻塞 `RENAME TABLE`，对精确记录的隔离库导入连接执行真实 `KILL CONNECTION`。结果为：

1. 原正式数据保留，23 张暂存表及精确持久映射存在。
2. 新备份明确拒绝；实际 HTTP 预览接口也拒绝待恢复状态，不再将暂存表收录成普通备份对象。
3. 导入页面返回带 CSRF 的恢复表单；POST `recoverimport` 返回 303，登记暂存表及待恢复记录均清除。
4. 原备份可重新通过实际 HTTP 预览，并确认导入成功，返回 303。

这解决了原报告的“连接失效后无法清理、原备份不能重试”场景。服务端不再依赖已经失效的旧连接完成恢复。

## DB02 与 DB03 共同剩余问题

**位置：**[写入取得槽位后直接执行](../system/common/database_gate.php#L51)，没有核验待恢复记录；[导入屏障退出](../system/common/database_gate.php#L76)释放所有槽位。[恢复的 `pre_swap` 分支](../system/common/backup_import.php#L120)把旧表换回，再删除承载当前正式数据的暂存表，但不识别这段时间里新确认的编辑。

**真实故障重放，InnoDB 与 MyISAM 内容表结果相同：**

1. 历史备份的草稿标题为 A，当前正式内容改为 C，启动真实导入；自动备份包含导入前状态。
2. 整体 `RENAME TABLE` 已完成，在后续 `SELECT * FROM f_view_field LIMIT 0` 核对期间终止导入连接。该连接回退失败；持久记录仍为 `pre_swap`，93 张旧表完整存在，当前正式表已经是导入后的 A。
3. 原请求退出后，普通后台编辑页面仍能打开。使用新取得的编辑签名提交 D，接口返回 **HTTP 200、`status=y`**；直接查询正式表，标题确实为 D。
4. POST 实际 `recoverimport`，返回 **HTTP 303**。恢复按映射回退至 C，并清除待恢复记录；查询正式表，D 已消失。D 发生在导入前自动备份之后，也没有被这次恢复保留。

两种引擎的直接中断均在第一次调度尝试捕获。这里没有手工执行交换来替代真实中断，也没有改变恢复分支。另在 23 表夹具上，使用真实中断生成的映射执行同一原子交换、构造可达的待提交状态，独立验证了相同的 HTTP 编辑及恢复结果；该状态构造与上述直接故障证据分开记录。

**影响：**普通管理员收到保存成功确认，却在稍后显式恢复时丢失该编辑。错误提示虽然要求立即暂停写入，服务端仍实际接受写入。因此活动请求内的屏障不能视为覆盖了整个待恢复生命周期。精确表名映射解决了“清理谁”，尚未解决“何时可以安全丢弃当前正式表”。

**修复要求：**在普通写入取得槽位之后、执行业务闭包之前，可靠检查同库待恢复状态；检查必须与恢复协议协调，覆盖等待槽位期间才产生的中断记录。中断记录未安全处理完毕时，内容、结构、上传及计数等写入应明确拒绝，不能提前确认。保留必要的登录、只读查看与受保护恢复通道，不能因一律拒绝 POST 而使站长无法进入恢复入口。

对于已经发生中断且可能接受过后续编辑的状态，恢复不能未经核对就丢弃这些数据；需要先保全、检测或明确要求人工处理。仅增加下一次请求的提示，不足以修复已确认写入的丢失。

**关闭验收：**在两种引擎下再次捕获交换后、提交记录前的真实连接中断；待恢复期间的普通编辑必须拒绝或得到可靠保留。恢复完成后重新打开编辑页，新保存应成功；原备份仍可重新预览和导入，且无非本操作对象被删除。补充排队写请求及独立上传的待恢复状态回归。当前 DB02、DB03 保留为 P2。

## DB04 关闭证据

[数据库锁等待](../system/common/backup.php#L55)现在设置为剩余预算内最多 5 秒，并配置连接超时；时间从进入备份起计入总预算。

保持阻塞连接的表写锁不释放，真实备份约 **5.01 秒**即报无法取得读锁，没有发布成功备份。之后释放测试锁，下一次备份成功，未发布的临时文件为 0。原报告需要保持到 132 秒的场景已经在数据库等待阶段提前结束，DB04 可以关闭。本轮不据此承诺所有主机的网络 I/O、代理硬超时或大库扫描耗时均相同。
