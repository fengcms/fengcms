## CM03 剩余问题 批量锁超时仍不报告已完成部分

**优先级：P2。状态：部分解决，暂不关闭。** 位置：[命名锁失败分支](../admin/app/model/contentWrite.php#L31)、[批量汇总](../admin/app/model/contentWrite.php#L125)、[cms_fail()](../system/common/security.php#L28)。

常规批量语义已经改善。上次的 `[已发布 A、已回收 B、已发布 C]` 回收请求现在返回 `changed=[A,C]`、`already=[B]`，三项最终均为回收状态；包含不存在 ID 的还原及永久删除会返回 `status=p`，后续记录也继续处理。

但 `locked()` 在 `GET_LOCK(...,5)` 超时后调用 `cms_fail()`。该函数直接 `exit`，不会成为 `batch()` 的 `catch (Throwable)` 可捕获异常，批量汇总随整个请求终止。

本轮独立重现顺序：

1. 创建状态均为 1 的 A、B、C。
2. 独立数据库连接持有与 B 后台写入相同的命名锁。
3. 正常认证和 CSRF 的 HTTP 请求按 `[A,B,C]` 批量回收。
4. A 完成回收；B 等待约 5 秒失败；请求直接返回 409。

| 观察项 | 实际结果 |
| --- | --- |
| 请求前状态 | `[1,1,1]`。 |
| 请求后状态 | `[-1,1,1]`。 |
| HTTP | 409。 |
| JSON | `status=n`、`error=1`、“内容正在由其他请求处理，请稍后重试。” |
| 批量明细 | 没有 `changed`、`already`、`missing`、`failed`，C 未处理。 |

这仍然是“前部已修改，但响应无法说明哪些完成”的原问题。本轮直接实测回收；还原和永久删除也需要纳入修复后的锁超时验收，不能仅依据常规分组用例通过就关闭。

**修复要求：**将可恢复的单项锁超时转换为批量层能够处理的结果或领域异常，保留已完成明细，并按已选择的部分完成契约处理后续项。单条接口仍可映射为 409，认证和 CSRF 校验不得被弱化。不要仅在批量外层再包一次 `try/catch`，它捕获不了 `exit`。

**补充验收：**分别让首项、中间项、末项锁超时，覆盖回收、还原、永久删除及属性操作；逐项比对返回分组与数据库状态，确认重试不丢失此前结果。若改为操作前整体获取锁，也必须证明失败时尚未产生写入。

## CM07 剩余问题 校验通过后仍可写入被删除的栏目

**优先级：P2。状态：部分解决，暂不关闭。** 位置：[保存前栏目检查](../admin/app/model/moduleModel.php#L84)、[普通编辑](../admin/app/model/contentWrite.php#L66)、[普通创建](../admin/app/model/contentWrite.php#L181)、[栏目删除](../admin/app/controller/classifyController.php#L128)。

现在 `validateCategory()` 能拒绝请求到来时已经无效的栏目。但校验在取得内容写入锁之前进行，普通 `edit()` 和 `create()` 真正写入时没有再次把栏目有效性作为写入条件。等待期间，栏目可能已经由正常后台操作删除。

本轮只用自己创建的数据，以两个编辑会话执行以下时序：

1. 内容初始为未分类，目标栏目 C 存在且属于同一模型，栏目下没有内容。
2. 独立连接预先持有目标内容的写入锁；编辑请求通过栏目检查后进入等待，数据库进程列表确认已经到达锁屏障。
3. 第二编辑通过实际 `classify&operate=delete&id=C` HTTP 接口删除 C，响应 200，数据库确认 C 已不存在。这里没有直接用 SQL 删除栏目来绕过后台约束。
4. 释放锁，原编辑请求继续执行。

| 场景 | 原请求结果 | 最终数据 |
| --- | --- | --- |
| 普通编辑，等待内容行命名锁 | 200，`status=y`。 | 记录保存了已不存在的 C。 |
| 普通新增，等待创建键命名锁 | 200，`status=y`，返回新 ID。 | 新记录也引用了已不存在的目标栏目。 |
| 批量转移，相同的栏目删除时序 | 400。 | 原栏目值保持为 0。 |

转移路径的 [SQL EXISTS 条件](../admin/app/model/contentWrite.php#L150)能够拒绝本次竞态，证明修复只覆盖了部分写入口。普通新增、编辑不能套用该路径的通过结论。

**修复要求：**把栏目关系保护延伸到实际新增和编辑写入，并与后台栏目删除等关系变更建立一致的协调规则。仅在等待锁之前查一次不够；仅在锁内重复 SELECT 而不考虑后续写入窗口，也不能宣称完全消除竞态。方案应兼容当前 MyISAM 旧表、InnoDB 表及允许的 `classid=0`。

**补充验收：**普通新增、编辑、批量转移分别在校验后阻塞，再由另一真实后台会话删除或变更目标栏目；请求必须明确拒绝或遵循已定义的关系更新语义，不能成功留下失效引用。拒绝的新增不能留下内容、额外计数或错误的完成请求状态。

## 已关闭六项的主要证据

CM01 使用显式 `isEdit` 区分新增默认值与已有值，已从[状态模板](../admin/template/system/form/status.html#L1)及数字等字段模板移除真假值回填判断。独立 HTTP 用例保留草稿与数字零；真实浏览器使用后台 iframe 和 wangEditor 页面完成一次内置文章普通保存，数据库仍为草稿，没有因编辑而发布。

CM02 的[回收流程](../admin/app/model/contentWrite.php#L87)先记录原始发布状态，重复回收不覆盖它；[还原流程](../admin/app/model/contentWrite.php#L96)按保存状态恢复，缺历史状态时采用草稿。原状态 0、1 及历史回收记录均作了实际请求验证。

CM04 通过同一 `ContentWrite` 数据库连接执行事务写入；涉及非事务表时执行补偿。本轮独立验证的组合如下：

| 内容表与相关计数 | 链接失败重复请求 | 修复条件后原键重试及重放 |
| --- | --- | --- |
| InnoDB，无相关计数 | 两次均 500，内容残留 0，请求状态 `failed`、记录 ID 清空。 | 成功且返回同一记录 ID。 |
| InnoDB，相关标签表为 MyISAM | 两次均 500，内容残留 0，标签热度不变。 | 只创建一次，标签热度增加一次。 |
| MyISAM，相关标签表为 MyISAM | 两次均 500，内容残留 0，标签热度不变。 | 只创建一次，标签热度增加一次。 |

链接故障只在独立临时模型中缩短生成链接列来注入，恢复后再重试。另将独立作者行的计数设到物理上限，使第二项相关计数更新失败，确认内容及前一项标签计数均已补偿；没有修改原业务表结构或引擎。

CM04 的关闭不表示 MyISAM 获得了进程崩溃原子性。[修复记录](CONTENT_WRITE_CONSISTENCY_FIX_2026-10-27.md)已经明确进程突然退出和提交结果未知需核查。`f3ad920` 的未知提交保护完成源码核对；本轮模拟持久化 `processing` 请求，重放返回 409 且没有创建记录，但未实施数据库断连导致 COMMIT 响应丢失的真实演练，该边界仍属待验证。

CM05 的[编辑签名和锁内核对](../admin/app/model/contentWrite.php#L66)使两个同时到达锁屏障的独立编辑请求返回 `[200,409]`，不再两次成功覆盖。旧签名保存不能撤销回收；无变更保存返回成功。真实浏览器中，另一个 HTTP 会话更新后，旧页面保存收到冲突，标题和正文仍留在编辑表单，数据库保留另一会话的已提交内容。界面先出现通用失败提示再出现冲突提示，存在提示重复，但不影响本项数据保护结论。

CM06 的[创建键及请求状态](../admin/app/model/contentWrite.php#L187)按账号、模型、键和规范化载荷关联。同账号两个 Session 同时到达创建锁，两次均返回 200、ID 相同，标签热度只增加一次；已完成请求的等效重放返回 `replayed=true`；同键改变标题返回 409。这里验证了请求重放，没有伪称真实丢弃过网络响应。

CM08 的[服务端字段规则](../admin/app/model/moduleModel.php#L114)在写入前拒绝必填空值、非数字及过长值；独立用例同时确认数字零及可选空值被保留。主回归中的内置文章及自定义数字字段用例也通过。
