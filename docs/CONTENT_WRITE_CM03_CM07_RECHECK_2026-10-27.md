## CM03 累积锁等待超过 HTTP 时限

**优先级：P2。状态：部分解决，保留。** 位置：[每次等待 5 秒](../admin/app/model/contentWrite.php#L33)、[逐条批量循环](../admin/app/model/contentWrite.php#L150)、[最多 500 个记录 ID 的入口](../system/common/security.php#L414)。

批量层现在能够收集单个超时，但没有整个请求的等待预算。每条记录独立等待最多 5 秒，累积等待可能长于 Web 服务器允许的响应时间；结果只在全部循环结束后输出。

本轮在独立临时模型中创建 14 条已发布记录，远低于接口接受的 500 条上限。第一条不加锁，独立数据库连接持有其余 13 条的记录命名锁，然后发送正常认证、CSRF 和 ID 列表的批量回收请求。没有修改 Nginx、PHP 或程序的超时配置。

| 观察项 | 本轮实际结果 |
| --- | --- |
| 批量规模 | 14 条，第一条可执行，其余 13 条等待记录锁。 |
| 客户端收到响应的耗时 | 约 60.02 秒。 |
| HTTP | 504。 |
| 响应体 | 网关错误页，没有逐条结果 JSON。 |
| 此时数据库状态 | 第一条已从 1 变成 -1，其余 13 条仍为 1。 |
| Nginx 日志 | 对应请求出现 `upstream timed out ... while reading response header from upstream`。 |

随后使用同一 Session 的请求等待原处理结束，确认后台已释放会话后才清理测试数据，没有把仍在运行的后台请求当成已撤销。

**影响：**即使每次锁超时已被正确捕获，批量仍可能在部分写入后无法向用户返回明细；网关 504 也不代表后台未执行或已回滚。本轮触发规模是本地环境的实测结果，其他主机的时限不同，不能把 14 当作通用安全上限。

**修复要求：**给批量执行增加小于实际响应时限的总预算，按剩余预算决定锁等待及是否继续处理；在预算耗尽前返回已完成、失败及未处理项，或采用可查询结果的后台任务。不能只调大网关超时或继续为每个 ID 无条件等待 5 秒。重试必须能对应已完成部分。

**补充验收：**保留已通过的 15 组单项超时用例；增加多个连续超时、有效项穿插、接近允许批量规模和预算耗尽后的重试。检查实际 HTTP 响应、数据库状态及未处理 ID，不能仅直接调用模型方法验证返回数组。

## CM07 跨模型父子栏目的递归删除未取得子模型关系锁

**优先级：P2。状态：部分解决，保留。** 位置：[按模型命名的关系锁](../admin/app/model/contentWrite.php#L49)、[编辑的关系锁和校验](../admin/app/model/contentWrite.php#L90)、[父栏目删除](../admin/app/controller/classifyController.php#L129)、[递归删除子栏目](../admin/app/controller/classifyController.php#L284)。

同模型的删除与内容写入已经使用同一关系锁。但删除父栏目时，只按父栏目的 `project` 取得关系锁，递归处理的子栏目可能属于另一模型。当前后台接受这种跨模型层级，不能假定整棵子树只有一个模型。

本轮使用两个独立临时内容模型 A、B，通过真实后台保存接口创建 A 模型父栏目 P、B 模型子栏目 C，并确认创建成功。没有直接往数据库强插一棵服务端拒绝的栏目树。随后：

1. 在 B 模型创建一条未分类内容，获取真实编辑签名。
2. 对该独立 InnoDB 内容行持有短暂 SQL 行锁，提交将其转到 C 的正常编辑请求。
3. 确认请求已通过栏目校验、持有 B 模型关系锁，并且实际 UPDATE 正在等待 SQL 行锁。
4. 第二编辑通过正常后台接口删除父栏目 P。删除端只取得 A 模型关系锁，仍然递归删除了 B 模型的 C。
5. 释放 SQL 行锁，编辑请求继续写入。

| 观察项 | 本轮实际结果 |
| --- | --- |
| 跨模型父子栏目创建 | 后台保存接口接受。 |
| B 模型关系锁 | 保存请求持有，数据库锁归属查询已确认。 |
| 父栏目删除 | HTTP 200，子栏目 C 已不存在。 |
| 原编辑保存 | HTTP 200，`status=y`。 |
| 最终内容数据 | B 模型内容保存了已删除的 C 的 ID。 |

这里不是绕开后台直接删除栏目，也不是仅凭一个极短的概率窗口推断；等待中的 UPDATE 和锁归属使上述时序可确定重放。

**影响：**单模型路径已被保护，但对子树操作仍可能破坏其他模型的栏目关联。在只持有根模型锁时，子模型的锁内校验也不能阻止另一模型的删除端移除目标栏目。

**修复要求：**按实际子树覆盖关系保护。如果沿用模型关系锁，需要协调子树涉及的全部模型，采用确定的加锁顺序，并保证检查到删除期间的子树变化也受约束；同时按每个子节点的实际模型处理内容。也可采用覆盖整棵子树关系变更的等效机制。不能只在普通保存端再查一次栏目，或只给父模型增加一次锁。若产品要限制跨模型挂载，应先明确规则和存量兼容方案，不能忽略目前后台接受的结构。

**补充验收：**同模型及跨模型两层、多层子树分别覆盖父栏目单条删除、批量删除和清空；与新增、编辑、转移交错执行。确认不会遗留失效关联、不会错误处理其他模型内容，也没有引入锁顺序死锁。保留上次已通过的同模型三条路径及创建无残留检查。
